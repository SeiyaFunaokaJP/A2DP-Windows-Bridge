## GUI モード（既定）

```
A2DPWB.exe
```

グラフィカルインターフェースでは以下の操作が可能です:

- **Bluetooth アダプター選択** -- 使用する WinUSB アダプターを選択
- **オーディオデバイス選択** -- WASAPI ループバックキャプチャのソースを選択
- **デバイスアドレス** -- 手動入力、ペアリング済みデバイスから選択、またはプロファイル画面の **デバイスを検索**（USB アダプターで近くのデバイスを検索）。入力・貼り付けたアドレスはその場で整形されます: `AA:BB:CC:DD:EE:FF`、`aa-bb-cc-dd-ee-ff`、`AABBCCDDEEFF`、`AA BB CC DD EE FF` はどれも `AA:BB:CC:DD:EE:FF` になります
- **コーデック選択** -- Auto / LDAC / aptX HD / aptX LL / aptX / SBC / AAC
- **LDAC 品質** -- HQ (990 kbps) / SQ (660 kbps) / MQ (330 kbps)
- **LDAC ABR** -- 不安定な接続時のアダプティブビットレート切替
- **プロファイル管理** -- デバイス + コーデック設定の保存・読み込み
- **リアルタイムステータス** -- コーデック、ビットレート、接続状態
- **通信品質** -- **操作 > 通信品質...**（[通信品質ウィンドウと AFH](#link-quality)を参照）
- **設定メニュー** -- 言語、テーマ、Windows 起動時に開始、システムトレイに最小化、起動時にアップデートを確認、ヘッドホンのボタンで再生を操作（[ヘッドホンのボタン](#headphone-buttons) を参照）、デバッグモード（**デバッグ** メニューが加わります: デバッグコンソール、HCI キャプチャ、対向受信テスト）

## CLI モード

`--cli` オプションで GUI なしで実行します。

### 基本

```bash
# 最適なコーデックを自動選択
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF
```

### コーデック選択

```bash
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac      # LDAC
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxhd    # aptX HD
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxll    # aptX Low Latency
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c aptx      # aptX
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c aac       # AAC
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c sbc       # SBC
```

自動選択の優先順位: LDAC > aptX HD > aptX LL > aptX > AAC > SBC

指定したコーデックをヘッドホンが提供していない場合、CLI は Auto の優先順位でフォールバックします。aptX Adaptive は選択されません -- [aptX ファミリーと aptX Adaptive の互換性](#aptx-compatibility)を参照してください。

### LDAC 品質

```bash
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q hq   # 990 kbps（既定）
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q sq   # 660 kbps
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q mq   # 330 kbps
```

### LDAC ABR（アダプティブビットレート）

```bash
A2DPWB.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -a
```

ABR は Bluetooth 接続が不安定な場合にビットレートを自動的に下げ、安定すると引き上げます。

### デバイス検出

```bash
# ペアリング済みの Bluetooth オーディオデバイスを一覧表示
A2DPWB.exe --cli -l
```

{: .note }
デバイス一覧の取得には WinUSB アダプターではなく、**内蔵** Bluetooth アダプター経由の Windows Bluetooth API を使用します。

### オプション一覧

| オプション | 説明 |
|:-----------|:-----|
| `-d <addr>` | ヘッドホンの Bluetooth アドレス（`AA:BB:CC:DD:EE:FF`） |
| `-c <codec>` | `ldac`、`aptxhd`、`aptxll`、`aptx`、`aac`、`sbc`、`auto`（既定: `auto`） |
| `-q <mode>` | LDAC 品質: `hq`（既定）、`sq`、`mq` |
| `-a` | LDAC ABR |
| `-m <mode>` | キャプチャモード: `loopback`（既定）、`virtual` |
| `--audio-device <id>` | `-m virtual` で使うオーディオデバイスの ID |
| `-u <path>` | アダプターの USB デバイスパス（複数接続している場合） |
| `-l` | ペアリング済みの Bluetooth オーディオデバイスを表示して終了 |
| `--max-packet <バイト数>` | 最大メディアパケットサイズ、679〜1679（[最大メディアパケットサイズ](#max-packet)を参照） |
| `--afh <auto\|off\|6,11>` | AFH ホストチャネル分類（[通信品質ウィンドウと AFH](#link-quality)を参照） |
| `--remote-sink <host[:port]\|auto>` | 対向受信機が受け取った内容を表示（[対向受信テスト](#receiver)を参照） |
| `-h` | ヘルプを表示 |

開発・テスト用に `--hci-tcp <host:port>`（WinUSB アダプターの代わりに TCP 経由の仮想コントローラー）、`--test-tone`（キャプチャ音声の代わりに左 1 kHz / 右 1.5 kHz）、`--duration <秒>`（指定秒数で停止）、`--hci-capture <file.pklg>`（実行全体の HCI キャプチャ）もあります。[ビルド](building#emu)を参照してください。

GUI モードでは、`--minimized` でシステムトレイに入った状態で起動します（**Windows 起動時に開始** が使います）。

## キャプチャモード {#capture-modes}

A2DPWB は 3 つのオーディオキャプチャモードに対応しています。モードによって、音声経路のどこを取り込むかが違います:

| モード | 取り込むもの |
|:-------|:-------------|
| システムループバック | Windows の既定の出力デバイスで再生される音（全アプリのミックス） |
| 仮想デバイス | 選んだデバイス（VB-CABLE 等）にアプリが出力した音 |
| アプリ | 1 つのアプリ（とその子プロセス）が再生する音だけを、アプリ自身の処理の後で取り込む。Windows 11 または Windows 10 バージョン 2004（ビルド 19041）以降が必要 |

プロファイル画面でも、**キャプチャソース**の下に同じ説明が表示されます。

システムループバックは音声をコピーするだけで、既定の出力デバイスから音声を奪いません。音声は Bluetooth ヘッドホンに加えて、そのデバイス（スピーカー、HDMI 接続のテレビなど）からも出続けます。ヘッドホンだけで聞くには、VB-CABLE などどこからも音が出ないデバイスを使って、仮想デバイスモードにしてください。

仮想デバイスモードでは、**既定デバイスを自動切替**（既定で有効）により、ストリーミング中は選択したデバイスが Windows の既定の出力になります。Windows の設定を変えなくても、アプリの音声がそのデバイスに出力されます。ストリーミングを止めると、元の既定デバイスに戻します。

- **オーディオデバイス**の一覧には、A2DPWB が仮想オーディオデバイスと判定したデバイスだけが表示されます。
- 既定の通信デバイス（通話アプリが使うもの）は変更しません。
- アプリによっては、再起動するまで元のデバイスで再生し続けます。
- A2DPWB が異常終了した場合、既定デバイスは元に戻りません。Windows のサウンド設定で変更してください。

### アプリモード {#application-mode}

アプリモードは、1 つのアプリ（音楽プレーヤー、ブラウザー、エフェクトアプリなど）の音声を送ります。**アプリ**の一覧から選んでください。一覧には現在音声を再生しているアプリが表示されます。見つからない場合は、そのアプリで再生を始めてから **更新** を押してください。子プロセスも含むので、別プロセスで音声を再生するブラウザーでも使えます。

- アプリが起動していなくても接続できます。A2DPWB はヘッドホンに接続し、アプリが起動すると送信を始めます。ストリーミング中にアプリを終了しても接続は保たれ、アプリを起動し直すと自動で再び取り込みます。
- アプリ自身の出力先デバイスからも音は出続けます。ヘッドホンだけで聞くには、その出力先デバイス（マスター音量）をミュートしてください。A2DPWB が取り込む音には影響しません。ただし、Windows の音量ミキサーでアプリ自体をミュートすると、ヘッドホンも無音になります。
- Windows の音量ミキサーにあるそのアプリのスライダーで、ヘッドホンに送る音量が変わります（出力先デバイスの音量も一緒に変わります）。マスター音量や音量キーでは変わりません。
- Windows が A2DPWB の指定したサンプルレートに変換するので、サウンド設定のデバイス形式に左右されません。
- Windows 10 バージョン 2004（ビルド 19041）より前には、アプリ単位のキャプチャがありません。その PC ではプロファイル画面にアプリモードが使えないと表示され、そのプロファイルで接続するとエラーになります。

### 音量 {#volume}

ストリーミング中、ヘッドホンが AVRCP 絶対音量に対応していれば、メイン画面に **音量** スライダーが表示されます。ヘッドホン側の音量を変えるので、送る音声のビット数は削られません。ヘッドホンの音量ボタンやタッチ操作で変えた値もスライダーに反映されます。

### ヘッドホンのボタン {#headphone-buttons}

ストリーミング中は、ヘッドホンの再生/一時停止・曲送り・曲戻しの操作（ボタンやタッチ操作。WH-1000XM4 のダブルタップなど）で PC の再生を操作できます。A2DPWB はこれを Windows のメディアキーとして渡し、Windows のメディアコントロールに表示されているアプリ（Spotify、ブラウザー、メディアプレーヤーなど）が受け取ります。停止も渡します。

- 再生と一時停止はどちらも Windows の再生/一時停止キーとして扱うので、ヘッドホン側の再生状態の認識がずれていても、タップのたびに再生と一時停止が切り替わります。
- A2DPWB は再生中かどうか（キャプチャする音声があるかどうか）をヘッドホンに伝えるので、外すと一時停止するヘッドホンも正しい操作を送れます。
- 早送り・巻き戻し（ボタンの長押し）は Windows に対応するメディアキーがないため無視します。
- 音量の操作はヘッドホン自体の音量を変えます（[音量](#volume) を参照）。Windows の音量は変わりません。
- **設定 > ヘッドホンのボタンで再生を操作** でオフにできます（別のプログラムもメディアキーに反応して二重に動く場合など）。

ヘッドホンが AVRCP に対応している必要があります（ほぼすべてのヘッドホンが対応しています）。対応していない場合も、ボタンが使えないだけでストリーミングは通常どおり動作します。

### システム全体のエフェクトアプリ {#effects-apps}

システム全体にかかるエフェクトアプリ（イコライザー、音質補正、バーチャルサラウンドなど）の多くは、自分の仮想出力デバイスを追加します。他のアプリはそのデバイスに音を再生し、エフェクトアプリは処理した音を、エフェクトアプリで選んだ出力先デバイスに再生します。A2DPWB でどのモードを選ぶかで、エフェクトがかかった音になるかが決まります:

| 設定 | ヘッドホンに届く音 |
|:-----|:-------------------|
| 仮想デバイス: エフェクトアプリ自身の仮想デバイス | エフェクト**前**の音（アプリがエフェクトアプリに渡す音） |
| アプリ: エフェクトアプリ | エフェクト**後**の音（エフェクトアプリが再生する音。おすすめ） |
| 仮想デバイス: エフェクトアプリの出力先デバイス（出力先を VB-CABLE にした場合など） | エフェクト後の音（アプリモードが使えない Windows 向け） |

アプリモードでは、エフェクトアプリの出力先はどのデバイスでも構いません。A2DPWB が取り込むのはアプリが再生する音で、デバイスが鳴らす音ではないので、出力先は音の行き先として置いておくだけです。PC でも同時に鳴らないように、誰も聞いていない出力（モニターの HDMI 音声など）を選ぶか、そのデバイスのマスター音量をミュートしてください。VB-CABLE などの仮想デバイスを音の捨て場にしてもよいですが、必須ではありません。出力先のデバイスは有効で、接続されている必要があります。

#### A2DPWB が自分の仮想出力デバイスを持たない理由 {#no-virtual-device}

Windows の出力デバイス一覧に Bluetooth ヘッドホンを出し、エフェクトアプリから直接選べるようにするには、カーネルモードのオーディオドライバーが必要です。A2DPWB はこれを含めていません:

- カーネルのオーディオドライバーを作って保守するのは大がかりな作業で、不具合があると Windows ごと停止（ブルースクリーン）します。
- Windows 10 / 11 は Microsoft の署名があるドライバーしか読み込みません。署名を受けるには EV コード署名証明書（年に数百米ドル）と Microsoft Partner Center のアカウントが必要で、通常は法人として登録します。
- 署名を回避する方法は Windows のテスト署名モードだけですが、システムのセキュリティが下がり、一部のソフト（アンチチートのあるゲームなど）が動かなくなります。A2DPWB はこの方法を使いません。

同じ用途には、アプリモードか、無料の仮想デバイス（VB-CABLE など）を使ってください。

- 既定デバイスを変更する公開 API は Windows にないため、他の音声切り替えツールと同じく非公開の IPolicyConfig インターフェースを使います（Windows 10 / 11）。

{: .warning }
どちらのモードも WASAPI 共有モードを使用するため、キャプチャのサンプルレートは Windows サウンド設定の「既定の形式」に依存します（通常 48 kHz）。LDAC の 96 kHz を利用するには、**サウンド設定 → デバイスのプロパティ → 詳細 → 既定の形式**で出力デバイスのサンプルレートを 96 kHz に変更してください。

## コーデック比較

| コーデック | 最適な用途 | トレードオフ |
|:-----------|:-----------|:-------------|
| LDAC (HQ) | 最高音質 | レイテンシーが高い、安定した接続が必要 |
| LDAC (ABR) | 音質 + 安定性 | 接続状況に応じてビットレートが変動 |
| aptX HD | 高音質、幅広いデバイス対応 | 固定 576 kbps |
| aptX LL | ゲーム、動画（低レイテンシー） | 音質が低い (16-bit) |
| aptX | aptX 対応機器が最も多い | 16-bit、352/384 kbps |
| AAC | Apple デバイス、良い効率 | 中程度の音質 |
| SBC | 最大の互換性 | 最低の音質 |

## aptX ファミリーと aptX Adaptive の互換性 {#aptx-compatibility}

A2DPWB は 3 種類の aptX コーデックに対応しており、いずれも [libopenaptx](https://github.com/pali/libopenaptx) でエンコードします。aptX Adaptive には**対応していません**。

{: .warning }
**aptX HD・aptX Low Latency は実験的な対応です。** Android / PipeWire の実装に合わせ、エンコード→デコードの往復テストは通っていますが、実機のヘッドホンでの検証はまだです。

{: .note }
**クラシック aptX だけが目的なら**、Windows 10 標準の Bluetooth スタックがクラシック aptX に対応しています（aptX HD・aptX LL・aptX Adaptive は非対応）。その場合 A2DPWB は不要です。A2DPWB が主に役立つのは LDAC・aptX HD・aptX Low Latency です。

| コーデック | Vendor ID / Codec ID | RTP ヘッダー | 対応状況 |
|:-----------|:---------------------|:-------------|:---------|
| aptX | 0x0000004F / 0x0001 | なし | 対応（44.1/48 kHz で 352/384 kbps） |
| aptX HD | 0x000000D7 / 0x0024 | あり | 対応（576 kbps、24-bit 入力） |
| aptX Low Latency | 0x0000000A または 0x000000D7 / 0x0002 | なし | 対応（352 kbps） |
| aptX Adaptive | 0x000000D7 / 0x00AD | -- | **非対応** -- 検出してログに記録するのみ |

### aptX Adaptive に対応していない理由

オープンソースの aptX Adaptive エンコーダーは存在しません。libopenaptx が実装しているのは aptX と aptX HD のみです（A2DPWB は aptX Low Latency にも使用しています）。[arkq/openaptx](https://github.com/arkq/openaptx) も aptX / aptX HD を再実装しているだけで aptX Adaptive エンコーダーは含まれておらず、バイナリの再配布も認められていません。そのため A2DPWB は aptX Adaptive を検出してログに記録するだけです。

### aptX Adaptive から aptX への「フォールバック」ではありません

接続時、ヘッドホンは対応コーデックの**一覧**（AVDTP ストリームエンドポイント）を通知し、A2DPWB はその中から 1 つを選びます。aptX Adaptive は最初から選択候補に入らないため、そこから「フォールバック」するわけではありません。

- **ヘッドホンがクラシック aptX も通知している場合** -- Qualcomm は aptX Adaptive を aptX / aptX HD と下位互換があると案内しているため、多くの aptX Adaptive 対応ヘッドホンがこれに該当します。この場合 A2DPWB はクラシック aptX を直接選択します。aptX はヘッドホンの一覧にある独立したコーデックであり、aptX Adaptive の縮退モードではありません。
- **ヘッドホンが aptX Adaptive のみを通知している場合**（クラシック aptX・aptX HD・aptX LL がない） -- A2DPWB では aptX を使えません。Auto は優先順位に従って次のコーデック（通常は AAC か SBC）を選びます。

自動選択の優先順位: LDAC > aptX HD > aptX LL > aptX > AAC > SBC

### 指定したコーデックがない場合の GUI と CLI の違い

ヘッドホンが通知していないコーデックを明示的に指定した場合、GUI と CLI で動作が異なります。

| モード | 動作 |
|:-------|:-----|
| GUI（Auto 以外のコーデックを指定） | エラー（「デバイスは ... に対応していません」）で接続を中止します。aptX・aptX HD・aptX LL を指定し、ヘッドホンが aptX Adaptive しか提供していない場合は、その旨を表示し Auto・AAC・SBC の使用を案内します。 |
| CLI（`-c <codec>`） | `Requested codec ... not available, falling back...` と表示し、Auto の優先順位で選択を続けます。ヘッドホンが aptX Adaptive を提供している場合は、それが選択されないことを示す行も表示します。 |

### サンプルレート

aptX・aptX HD・aptX LL が対応するのは 44.1 kHz と 48 kHz のみです。A2DPWB はヘッドホンが通知したサンプルレートから 1 つを選び（現在の Windows デバイスのレートを優先し、使えなければ 48 kHz）、WASAPI にリサンプリングさせます。aptX のために Windows のサウンド設定を変更する必要はありません。

### ヘッドホンが提供するコーデックの確認方法

1. **設定**メニューで**デバッグモード（debug.log / HCI ログを出力）**にチェックを入れ、A2DPWB を再起動します。
2. ヘッドホンに接続します。
3. 設定フォルダー（`%APPDATA%\A2DPWB`）の `debug.log` を開きます。CLI モードでは同じ内容が標準エラー出力に書き出されます。

GUI では **デバッグ > デバッグコンソール...**（Ctrl+Shift+D）でも同じログをリアルタイムに確認できます。上段の**接続フロー**には、直近の接続の各段階（アダプター初期化、ACL / AVDTP 接続、コーデック能力の取得、コーデック選択、WASAPI、ストリーム設定、エンコーダー、ストリーム開始、音声送信、切断・再接続）が OK / 警告 / 失敗として並び、行をダブルクリックすると根拠になったログ行へ移動します。下段のログはレベルと文字列で絞り込めます。**診断情報をコピー**は、バージョン・OS・アダプター・プロファイル・接続フロー・警告とエラー・直近のログをまとめてクリップボードへコピーします（不具合報告にそのまま貼れます。既定では Bluetooth アドレスの下位 3 バイトを伏せます）。

以下の行で、ヘッドホンが通知しているコーデックを正確に確認できます。

```
BTstack: Remote supports aptX (SEID=..., caps=0x..)
BTstack: Remote supports aptX Adaptive (SEID=...) — never selected (no open encoder); classic aptX is used only if the remote lists it
BTstack: Remote vendor codec vid=0x........ cid=0x.... (SEID=...) — unsupported
BTstack: Capability discovery complete (LDAC=0, aptXHD=0, aptXLL=0, aptX=1, aptXAdaptive=1 [not encodable], SBC=1, AAC=1)
```

- `aptX=1` -- クラシック aptX を使用できます（`aptXAdaptive=1` であっても同様）。
- `aptX=0`・`aptXHD=0`・`aptXLL=0` かつ `aptXAdaptive=1` -- ヘッドホンは aptX Adaptive しか提供していません。Auto・AAC・SBC を使ってください。
- `Remote vendor codec ... — unsupported` -- A2DPWB が実装していないその他のベンダーコーデックです。

## 最大メディアパケットサイズ（プロファイルごと） {#max-packet}

各プロファイルの **最大メディアパケットサイズ**（**プロファイル編集**。CLI では `--max-packet <バイト数>`）で、Bluetooth パケット 1 つに入れる音声データの上限を 679〜1679 バイトの範囲で設定できます。ヘッドホンごとに別の値を使えます。ヘッドホン側の上限（MTU）も常に適用され、A2DPWB は小さい方を使います。変更は次回の接続から反映されます。以前のバージョンで保存したプロファイルには、それまで全体で設定していた値が入ります。

**既定値の 1023 を推奨します。** Bluetooth のベースバンドパケット（3-DH5）1 つに収まる大きさです。大きくしても削減できるオーバーヘッドは 1〜2% 程度で、パケットが失われたときに失われる音声が長くなります。679 は 2-DH5 パケット 1 つ分で、LDAC が受け付ける最小値です。

## 送信ストリームの検証（a2dpwb_decode） {#verify-stream}

多くのヘッドホンは、使用中のコーデックを表示できません。デバッグモードでは GUI に **デバッグ** メニューが表示され、**HCI キャプチャを開始** / **HCI キャプチャを停止** を選べます。キャプチャは HCI パケットログ（設定フォルダーの `hci_<日付>_<時刻>.pklg`）で、コーデックの交渉内容と送信したすべてのメディアパケットが記録されます。LDAC 990 kbps では 1 時間あたり約 0.5 GB 増えるため、必要な間だけ記録してください。

キャプチャは接続前でもストリーミング中でも開始できます。接続中に開始した場合は、A2DPWB が記憶していた接続確立時のパケット（L2CAP チャネルの確立と、コーデック交渉を含む AVDTP シグナリング）を先に書き込むので、途中からでも解析できます。停止すると、保存したファイルのパスが表示されます。

キャプチャは Wireshark で開けるほか、開発者向けツール `a2dpwb_decode`（ソースからビルド。[ビルド](building)を参照）で検証できます。

```
a2dpwb_decode "%APPDATA%\A2DPWB\hci_20260925_120000.pklg" -o C:\temp\check
```

このツールは AVDTP シグナリング（SET_CONFIGURATION / RECONFIGURE と、ヘッドホンがそれを受け入れたか）を追跡し、A2DPWB が送信したメディアパケットを取り出して、交渉した設定と照合します。

| コーデック | 検証内容 | 出力 |
|:-----------|:---------|:-----|
| SBC・AAC・aptX・aptX HD・aptX LL | リファレンスデコーダーで全体をデコード。フレームのパラメーターと設定の一致、メディアペイロードヘッダーのフレーム数 | 試聴用の `<prefix>.<n>.<codec>.wav` |
| LDAC | フレームヘッダーのみ（同期ワード、サンプルレート、チャンネルモード、フレーム長）、フレーム数、ビットレート。オープンソースの LDAC デコーダーは存在しません | レポートのみ |

各ストリームについて、RTP シーケンス番号の欠落、RTP タイムスタンプの進み方、ビットレート、Bluetooth コントローラーが送信完了を報告した ACL パケット数も表示します。最終行は `RESULT: OK` か `RESULT: PROBLEMS FOUND` です（終了コード 0 / 1）。

{: .note }
これで分かるのは、A2DPWB が何を送信したかと、その内容が交渉したコーデックとして正しいかです。受信側は交渉したコーデックでしかデコードできないため、ヘッドホンから正しく音が出ていて、かつレポートに問題がなければ、そのコーデックが実際に使われている強い根拠になります。

## 通信品質ウィンドウと AFH {#link-quality}

**操作 > 通信品質...** には、ストリーミング中に A2DPWB が送信している内容を表示します: コーデックとビットレート、送信パケット数、送信前に破棄したパケット（送信キューがあふれた = 電波が追いつかない）、エンコーダが追いつかず落ちた音声、送信キュー、そして **電波**: 接続の RSSI（コントローラーの適正な受信範囲との差。0 なら適正、マイナスは弱すぎ。絶対値ではありません）と、79 ある Bluetooth チャネルのうちホッピングに使っている数（AFH）。

Bluetooth は混んだチャネルを自分で避けます（AFH）が、Wi-Fi のことはエラーから学ぶしかありません。A2DPWB は、避けるべきチャネルをコントローラーにも伝えます（AFH ホストチャネル分類）。すべての接続に適用されます:

| `afh` | |
|:--|:--|
| `auto`（既定） | この PC で強く聞こえる 2.4 GHz の Wi-Fi（Windows の Wi-Fi スキャン。接続中は繰り返し） |
| `off` | 伝えない（コントローラーに任せる） |
| `6,11` | 指定した Wi-Fi チャネル |

Bluetooth のチャネルは常に 20 以上残します。設定は `settings.json`（設定フォルダ）の `"afh"`、対向受信テストのウィンドウ（そこで保存されます）、CLI モードの `--afh` で行います。避けている Wi-Fi チャネルは「電波」の行に表示されます。効果は環境次第なので、対向受信テストで測って確かめてください。

## 対向受信テスト（tools/linux_sink） {#receiver}

通信品質ウィンドウに表示されるのは A2DPWB が送信した内容です。実際に何が届いたかを見るには、Linux の 2 台目の PC で `tools/linux_sink/a2dpwb_sink.py` を起動します。その PC の普通の Bluetooth アダプター（内蔵で可）を直接（Bumble、HCI ユーザーチャネル）A2DP シンクとして動かし、LDAC を含む全コーデックで届いたメディアパケットをすべて測定して、統計をネットワーク経由で提供します。

`tools/linux_sink` フォルダを Linux PC にコピーして（フォルダだけで動きます）、次を実行します:

```bash
sh setup.sh      # 初回のみ: デコーダーライブラリと Python 環境（Ubuntu / Debian、Python 3.11 以上）
sudo sh run.sh   # 受信側を起動（Bluetooth アダプターを使うため root）
```

デバッグモードの **デバッグ > 対向受信テスト...** を開くと、ローカルネットワークから受信側を自動で見つけます。**開始** を押すと、一定のテストトーン（またはシステム音声）を、選んだコーデック・品質・サンプルレート・ビット深度で受信側の Bluetooth アダプターへ送信します（プロファイルやペアリングの操作は不要）。送信した内容と届いた内容を並べて表示します: ビットレート、欠落・遅延パケット（RTP シーケンス番号）、ジッタと間隔、模擬した再生バッファの音切れ・音飛び、ストリーム／デコードのエラー、受信側の RSSI（適正な受信範囲との差。0 なら適正、マイナスは弱すぎ）。各手順（受信側の検出、統計の接続、受信側の設定、Bluetooth 接続、コーデック設定、音声の受信）を OK / NG で表示し、ログはコピーできます。CLI モードでは `--remote-sink auto` で同じことができます。受信側を見つけ、`-d` がなければその受信側へ送信し、統計を 5 秒ごとと終了時に表示します。

パケット数は送信側・受信側ともストリームの最初のパケットから数え、**停止** の後も最終値を「停止時」として表示したままにします（受信側の値は 1 秒ほど遅れて届きます）。送信数と受信数を比べられ、通常は一致します。Bluetooth は届かなかった無線パケットをコントローラーの中で再送し、A2DPWB はリンクが続く限りパケットをあきらめないため、電波が悪いときは欠落ではなく受信側の間隔・ジッタ・音切れとして現れます。電波が追いつかないときは、送信側で送信前に破棄されます。再送の回数は送信側・受信側のどちらからも取得できません。

ツールの実行中、受信側 PC の Bluetooth スタックはそのアダプターを使えません。検出は UDP ブロードキャスト（ポート 51201）なので、2 台は同じネットワークセグメントにある必要があります（そうでなければアドレスを入力します）。オプションと統計のプロトコルは `tools/linux_sink/README.md` を参照してください。

## トラブルシューティング

### アップデート後にペアリングがうまくいかない

A2DPWB は SSP（Just Works）と **General Bonding** でペアリングし、リンクキーを保存するため、次回以降はペアリングし直さずに再接続できます。以前のバージョンの A2DPWB でペアリングしていた場合は、ヘッドホン側で A2DPWB のペアリング情報を削除し（ペアリング履歴の消去方法はヘッドホンの説明書を参照）、改めてペアリングしてください。

### 接続がタイムアウトする

A2DPWB は SDP レコード（A2DP Source、AVRCP Controller / Target）を登録し、ヘッドホンがオーディオソースとして認識できるようにしています。接続がタイムアウトした場合は中途半端な接続が破棄されるため、A2DPWB を再起動せずにそのまま再試行できます。ヘッドホンの電源が入っていること、通信範囲内にあること、他の機器に接続されていないことを確認してください。

接続が確立した後に通信が届かなかった場合と、ヘッドホンが応答しなかった場合は、自動で再試行します（最大 3 回）。ヘッドホンがペアリング情報を失っている場合（リセットや別の PC とのペアリング）は、保存したキーを破棄して 1 回だけペアリングし直します。失敗したときは、何が起きたかを表示します:

| メッセージ | 意味 |
|:--|:--|
| デバイスが応答しません | 電源オフ、範囲外、または接続できない状態（新しいデバイスはペアリングモードに） |
| 接続は確立しましたが、その後の通信が届きませんでした | 電波状態: もう一度試すか、アダプターとデバイスの位置を見直す |
| デバイスは応答しましたが、デバイス側から接続を切られました | 今は接続を受け付けない状態: 電源を切る途中、充電中、別の機器と接続中など |
| 認証に失敗しました（ペアリングし直しても失敗） | デバイスをペアリングモードにするか、デバイス側のペアリング情報を削除して再試行 |
