## 窗口

从“开始”菜单启动 **A2DP Windows Bridge**（或运行 `a2dpwb.exe`）。左侧菜单包含以下页面（主页、编解码器、音频设备、适配器、诊断、设置、关于，以及开发者模式下的开发者）；窗口较窄时，菜单会折叠为图标。窗口只显示常驻程序 `a2dpwb-core.exe` 的运行情况：关闭窗口不会停止串流（请参阅[托盘与浮出窗口](#tray)）。

### 主页

- 每个已保存的音频设备一张卡片，并排显示：其状态、电量，以及已连接的设备所用的编解码器（以列表代替其名称，见下文）和比特率。如果使用的编解码器与所选的不同，编解码器一行会在几秒内于其名称旁说明原因，例如 **aptX Adaptive（不支持 Opus）**（或*被占用*、*为实验性*），之后只保留其警告标记（将鼠标悬停其上可查看原因）；状态行只显示**已连接**
- 每张卡片下方的**连接** / **断开连接**。同一时间只连接一台设备：在另一台设备上单击**连接**，会断开当前使用的设备并连接那台设备
- **音量**：耳机的音量（请参阅[音量](#volume)）；单击扬声器图标即可静音（发送静音），再次单击取消静音。其他设备的卡片也保留该滑块，但处于禁用状态
- 当前使用设备的编解码器，可在其卡片上的列表中选择以快速切换（例如游戏用一种、音乐用一种）：列出设备支持的编解码器（与[编解码器](#codecs)页面相同的选项），只显示名称。**自动选择**开启时也显示正在使用的编解码器；选择某个编解码器会关闭自动选择（可在编解码器页面重新开启）。选择后立即生效（设备会用它重新连接；与编解码器页面一样，下一次选择会等到设备连接完成）
- 当前使用设备的链路质量，带一个小图表，显示在卡片下方。输出源在**音频设备**中选择；设为输出源的应用程序尚未运行时，设备的卡片会显示这一点
- 出现错误时会显示原因，并在可能时附上解决问题的按钮（**替换为 WinUSB 驱动程序**、**打开下载页面**、**重新启动 Bluetooth**、**重试**、**编解码器**、**音频设备**等）

侧边栏在每个页面上都会显示每台设备的同样内容，托盘浮出窗口则显示当前使用的设备。

### 编解码器 {#codecs}

每个已保存音频设备的编解码器，每台设备一个分区（设备连接期间为绿色的圆点、名称、**已配对** / **音频**标记；地址位于**音频设备**中），其下是该设备的编解码器卡片，按音质从高到低排列（除非你自行调整了顺序），各带三个指标条（音质、低延迟、稳定性），并显示设备上次连接时是否提供了它：**支持**（绿色标记）或**不支持**（红色标记）。开启**仅显示支持的编解码器**（默认）时，显示的卡片无需也不带**支持**标记。华为和荣耀耳机会保留其 **LDAC** 卡片（显示为**未知**），直到它们列出 LDAC：它们可能只在选择了 LDAC 之后才会列出。所有编解码器都会提供；实验性编解码器（README 编解码器表中的 🧪）只在文档中标注。

- **自动选择支持的音质最高的编解码器**（页面顶部，适用于所有设备的设置；默认开启）：每个设备使用其支持的音质最高的编解码器，顺序为：LHDC V5 > LDAC > aptX Adaptive > Opus > aptX HD > aptX > aptX LL > AAC > SBC XQ > SBC，并采用其最佳设置：高音质、编解码器支持时为 24-bit，以及设备列出的最高采样率（例如 LDAC 96 kHz、LHDC V5 最高 192 kHz；aptX Adaptive 为 48 kHz，请参阅 [aptX Adaptive](#aptx-adaptive)；Windows 自身的采样率会被重采样）。开关下方的一行说明：关闭它即可自行选择、设置编解码器并调整其顺序。卡片为只读，按默认顺序排列，正在使用（或将由“自动”选择）的编解码器会突出显示；单击卡片或其 **...** 会询问是否关闭自动选择（**关闭自动选择** / **取消**）；关闭后，所单击的卡片即被选中（其 **...** 会打开其设置）。关闭后可为每个设备自行选择编解码器及其设置；尚未选择的设备沿用“自动”的选择。开启期间，为各设备选择的编解码器会被保留。如果 2.0.2 之前的设置为某个设备选择过编解码器，则初始为关闭
- 关闭时，单击卡片即可选择该设备的编解码器；选择会立即保存，正在串流的设备会用它重新连接。单击设备不支持的卡片（关闭**仅显示支持的编解码器**时显示）不会有任何变化。之前选择的、设备已不再提供的编解码器，会回退到该设备顺序中第一个受支持的卡片：除非你更改了顺序，否则就是它支持的最佳编解码器（请参阅[明确指定的编解码器不可用](#codec-fallback)）
- 关闭时，拖动设备的卡片（按住按钮时显示手形；或在卡片上按 Alt 加方向键），即可按自己的顺序排列其编解码器；每台设备保留各自的顺序。尚未选择编解码器的设备使用它支持的第一张卡片，所选编解码器不受支持时也是如此。FastStream 和 Opus 05 无论排在哪里，除非被选择，否则从不使用。**重置编解码器顺序**可还原顺序；它只在显示的卡片不是默认顺序时出现（移回原位后即恢复为默认顺序）。自动选择时不使用该顺序。如果正在串流的设备的编解码器因此改变，设备会重新连接
- 为正在串流的设备选择其他编解码器时，会用该编解码器重新连接。之后卡片（以及主页和托盘浮出窗口中的编解码器列表）会等到设备重新连接后才接受下一次选择，因此快速连续点击不会中断仍在建立的连接。切换编解码器不会显示连接通知；连接设备时会显示
- **仅显示支持的编解码器**（默认开启；关闭后将同时显示支持和不支持的编解码器）：设备没有提供的编解码器会被隐藏。设备首次连接之前，会显示全部编解码器
- 卡片上的 **...** 会打开该编解码器的设置。更改立即生效：对于正在使用的编解码器，设置会被保存，设备会用它重新连接，但 **Bitpool** 例外，它会在收听时直接改变；对于其他编解码器，设置会保留到选择该编解码器时使用。每种编解码器各自保留自己的设置：选择另一种编解码器再切换回来，原来的设置会恢复。只提供该编解码器支持的、且设备在上次连接时列出的选项：
  - **音质**：LDAC **高** / **中** / **低**（990 / 660 / 330 kbps）；LHDC V5 **高** / **中高** / **中** / **低**（1000 / 900 / 500 / 400 kbps，即 Android 的四个级别）；aptX Adaptive **高** / **低延迟**（请参阅 [aptX Adaptive](#aptx-adaptive)）。AAC、Opus、Opus 05、SBC 和 SBC XQ 只有一个级别 **高**，只显示而不可选择：即设备接受的最高比特率（如有 ABR 或 VBR，比特率仍会变化；SBC 和 SBC XQ 显示由其 bitpool 和帧设置得出的比特率）。aptX、aptX HD、aptX LL 和 FastStream 的比特率由编解码器固定。早期版本保存的、编解码器已不再提供的音质（aptX Adaptive 的标准 / 移动、AAC 的较低级别等）会按“高”加载
  - **自适应比特率 (ABR)**：用于 LDAC、LHDC V5、aptX Adaptive、SBC 和 SBC XQ（请参阅 [ABR](#abr)）；AAC 为 **VBR**
  - **采样率**：“自动”为 48 kHz；设备未列出 48 kHz 时，使用其列出的最佳采样率（96 kHz 会增加延迟和兼容性问题，却听不出差别，而且 Windows 以 48 kHz 混音）。如需 96 kHz，请在此处选择。只提供设备列出的采样率（aptX Adaptive 的 96 kHz 只提供给列出它的设备，请参阅 [aptX Adaptive](#aptx-adaptive)）
  - **位深度**：LDAC 和 LHDC V5 为 16 或 24 bit（“自动”：24 bit），以设备列出的为限；其他编解码器为 16 bit
  - **Bitpool**（SBC、SBC XQ）：一个带两个滑块的滑动条，分别为最小和最大 bitpool，范围为设备列出的范围。最大值就是所用的 bitpool；最小值是所用的最低 bitpool（建立连接时所用范围的下限，也是 ABR 可降到的下限）。**自动**会将两者恢复：最大值按音质决定，最小值为设备和 ABR 自身的值。其下一行显示声道模式，每种编解码器固定：SBC 为联合立体声，SBC XQ 为双声道。
  - **帧结构**（SBC 和 SBC XQ，仅开发者模式）：块数、子带数、比特分配，以及 SBC 的声道模式。Auto 保持 16 块、8 子带、Loudness 和 Joint stereo。设备不接受的值在连接时回退为 Auto。在一位用户测试的 Sony 设备上，12 块会使声音失真并可能断开连接（编码器的输出能正确解码；其他块数可正常播放）。关闭开发者模式后，这些选择仍会保存，但不会使用。AAC 和 LHDC V5 的比特率不会超过设备列出的最大值

默认值即可获得最佳音质；大多数设备只需保持**自动**。LE Audio 设备（实验性）只有一张 LC3 卡片，以及**游戏音频设备低延迟（实验性）**（请参阅 [LE Audio](#le-audio)）。

在后台，A2DPWB 在 `profiles.json` 中为每台设备保留一个条目（其编解码器、各编解码器的设置及其编解码器顺序），在其中命名为“*设备* | *编解码器*”；窗口和托盘菜单显示设备的名称。早期版本允许为同一台设备建立多个配置文件：首次启动带有“编解码器”页面的版本时，会保留最近使用的那个（否则保留第一个），并把其他的合并进去，同时为它们各自的编解码器保留其编解码器设置（音质、采样率、位深度、ABR、SBC 设置）。它们自己的名称、输出源和数据包大小不会保留；原来的 `profiles.json` 会作为 `profiles-before-codecs.json` 在设置文件夹中保存一次。2.0.2 预发布版本中的**自动选择的顺序…**（适用于所有设备的单一顺序，位于开发者模式中）已不再使用：现在每台设备都有自己的顺序。

### 音频设备

A2DPWB 可以串流到的耳机和扬声器，各有自己的设置：**扫描设备**会通过 USB 适配器查找附近的设备（30 秒，设备应答后即列出；**停止**可结束扫描；请让耳机进入配对模式）。A2DPWB 之前配对过的设备会标记为**已配对**。如果扫描找不到耳机，请在**手动：**下输入地址并单击**使用**；输入或粘贴的地址会自动格式化（`aa-bb-cc-dd-ee-ff`、`AABBCCDDEEFF` 和 `AA BB CC DD EE FF` 都会变为 `AA:BB:CC:DD:EE:FF`）。已保存的设备可以重命名或移除（移除时也会删除其设置和配对信息，因此在重新配对之前无法再连接），并具有：

- **输出源**：系统环回（新设备的默认值）、虚拟设备或应用程序（请参阅[捕获模式](#capture-modes)）。旁边显示 Windows 混合所捕获设备时使用的格式（采样率和位深度，只读）；当设备的编解码器设置要求其他格式时显示为琥珀色，并在下方用一行说明所需的格式（仍会转换后继续串流）；再下方是该输出源的说明
- **连接期间设为 Windows 默认输出设备**，使用虚拟设备时

列表上方的**所有音频设备**包含适用于每台设备的开关：**Windows 音量同步**（请参阅[音量](#volume)）、**用音频设备的按钮控制播放**和**自动重新连接**。每台设备的**最大媒体数据包大小**位于**开发者**页面（请参阅[最大媒体数据包大小](#max-packet)）。

### 诊断

- 串流期间的**链路质量**：实际比特率、数据包、发送前丢弃的数据包、捕获时丢弃的音频、发送队列、无线占用时间、信号（RSSI）以及 AFH 信道（请参阅[链路质量与 AFH](#link-quality)）
- 串流期间的**编解码器详情**：媒体负载、标头、编解码器帧和每个数据包的帧数，以及设备端点列出的内容与实际使用的内容：SBC 为 bitpool、采样率、声道模式、块数、子带数和比特分配；AAC 为对象类型、采样率、声道、峰值比特率和 VBR；其他编解码器为采样率、位深度和峰值比特率
- **连接流程**：最近一次连接尝试的十一个阶段（开始、Bluetooth 适配器、ACL / AVDTP 连接、功能发现、编解码器选择、音频捕获、流配置、编码器、流开始、音频发送、包括断开 / 重新连接在内的连接维持），各标记为“正常”、“警告”或“失败”，并显示所用时间。**复制流程**可复制这些内容
- **日志**：实时显示，可按级别（所有级别、信息及以上、警告和错误、仅错误）、文本以及当前连接尝试（**仅当前尝试**）筛选。**复制显示的日志**可复制当前显示的内容。**打开日志文件夹**会打开日志文件所在的文件夹；与**复制诊断信息**不同，这些文件不做隐藏处理（其中包含 Bluetooth 地址和你的 Windows 用户名）
- **开始 HCI 捕获** / **停止 HCI 捕获**（请参阅[验证媒体流](#verify-stream)）
- **复制诊断信息**：将版本、操作系统、适配器、音频设备（编解码器、其设置和顺序）、连接流程、警告 / 错误以及最近的日志复制到剪贴板，可直接粘贴到错误报告中。**隐藏 Bluetooth 地址**（默认开启）将地址替换为 `<addr-1>`、`<addr-2>`...（适配器自身为 `<adapter>`），设备名称替换为 `<device-1>`、`<device-2>`...，并隐藏 USB 序列号、应用自身文件夹以上的文件路径（`<path>\A2DPWB\logs\...`）以及你的 Windows 帐户（用户名和 SID）。为错误报告复制的崩溃报告和错误文本也采用同样的隐藏处理
- **报告问题**：
  - **详细日志**：**详细（debug）**或**全部（trace，1 小时）**会记录多得多的 Bluetooth、USB、音频捕获和编码信息。debug 会保持开启 24 小时，重新启动后也保持（便于排查启动时的问题），之后自动关闭。请先开启，重现问题，然后保存诊断包
  - **诊断包 > 保存…**：选择是否包含 HCI 捕获（除非有人要求你提供，否则保持关闭：其中保留了地址和设备名称），以及是否在文本文件中隐藏 Bluetooth 地址，然后保存为一个 `.zip`（位于设置文件夹的 `logs\bundles\` 中，保留最新的 3 个）：其中包括诊断信息、核心、窗口和驱动程序辅助程序的日志文件、崩溃报告、系统信息（USB Bluetooth 适配器及其驱动程序、Windows 中已配对的设备、音频设备）、设置以及每台设备的编解码器设置（绝不包括链接密钥），还有 HCI 飞行记录器。HCI 捕获保留地址（不含配对密钥）。会尽量控制在 GitHub 的 25 MB 附件上限以内（优先保留最新的日志，最多 48 MB 文本、最新的 5 个记录和 2 个小型转储）
  - **在 GitHub 上报告**（保存后）：新建一个错误报告，其中已填好版本、Windows 内部版本、适配器、耳机、编解码器、捕获模式和诊断信息（地址已隐藏），并在资源管理器中显示诊断包，以便将其拖入报告

A2DPWB 还会一直记录一些内容，这样即使问题只发生过一次，也仍然可以查看：

- **HCI 飞行记录器**：最近几分钟的 Bluetooth 通信保存在内存中（媒体负载被截短，配对密钥被移除），每当串流失败或连接丢失时保存到 `logs\hci\`（保留最新的 10 个文件）
- **崩溃报告**：如果 A2DPWB 崩溃，会将一个 `.dmp` 小型转储和一个 `.txt` 文件写入 `logs\crash\`（每个程序保留最新的 5 个）

磁盘占用有上限：正常情况下一天的日志远小于 1 MB，保留 7 天；开启详细日志时，一天的文件中 debug 和 trace 行最多占用 100 MB（之后直到第二天只记录信息及以上级别）；飞行记录器的文件最多几 MB，保留 10 个。

### 开发者 {#developer}

在**设置 > 开发者模式**开启时显示；大多数用户从不需要它。它用于测试设备和排查问题：其中部分设置只对某些设备有效。共五个选项卡：

- **应用设置**：**使用音量合成器**（默认关闭）：**音量合成器**页面、浮出窗口中的应用列表以及输出静音（请参阅[捕获模式](#capture-modes)）。不推荐使用；要让 PC 不发声，VB-CABLE 是更好的方法
- **编解码器设置**：用于查明设备为何没有声音的开关（RTP 标记位、记录最初的媒体数据包、AAC 配置和编码器选项）、每台已保存设备的**最大媒体数据包大小**（请参阅[最大媒体数据包大小](#max-packet)），以及**强制使用不支持的编解码器连接**：开启后，**编解码器**页面可以选择设备未列出的编解码器，A2DPWB 会向设备请求该编解码器，而不是回退。它只在关闭自动选择时生效。大多数设备会拒绝，连接随之以“无法设置编解码器”结束；接受的设备也可能没有声音。**自动选择编解码器时也使用各编解码器的设置**：开启自动选择时，编解码器卡片的 **…** 会直接打开而不关闭自动选择，“自动”选择的编解码器会用这些设置连接，而不是“自动”的设置。**让采样率和位深度匹配电脑的输出**：设为“自动”的采样率或位深度会跟随 Windows 声音设置中输出设备的格式（在编解码器和设备支持的范围内），而不是 48 kHz。**LHDC V5：忽略设备的最大比特率**：即使设备列出的最大值更低，LHDC V5 也以所选音质的比特率（最高 1000 kbps）运行，**编解码器**页面会提供所有音质。超过其最大值时，设备可能断续或无声。以上全部默认关闭，并在下一次串流开始时生效；只要有一项开启，就会有横幅提示。**全部关闭**可将它们全部重置
- **日志**：日志文件的保留时间（默认 7 天）、每日大小上限（默认 100 MB）、保持开启的详细日志（没有 24 小时或 1 小时的限制，并且从核心启动时就开始）、每 10 秒一次的串流健康状况行，以及**添加标记**（在日志中写入一行带编号的标记，便于再次找到某个时刻）。关闭开发者模式后会恢复为默认值
- **对端接收器测试**：向另一台 PC 上的测量用接收器串流，并比较发送的内容和到达的内容（请参阅[对端接收器测试](#receiver)）
- **芯片**：在使用 WinUSB 的适配器上运行芯片脚本，即输入或从文件打开的对芯片的请求，供想为某个芯片添加支持的人使用（请参阅[添加芯片支持](chip-support#chip-scripts)）。可能更改芯片的行只有在单击**允许运行**后才会运行；期间蓝牙会停止，下次使用时重新启动

## 托盘与浮出窗口 {#tray}

无论窗口是否打开，A2DPWB 都会在系统托盘中持续运行：

- **左键单击**托盘图标会打开浮出窗口：设备及其状态、**连接** / **断开连接**、音量、设备切换器、编解码器（与主页一样可从列表中选择）、链路质量以及**打开应用**。其高度与所显示的内容恰好一致。按 Esc 或单击其他位置即可隐藏。如果某个错误需要用到主窗口的某个页面（编解码器、音频设备、适配器），其按钮会打开窗口并转到该页面。开启**设置 > 单击托盘图标打开主窗口**时（默认关闭），左键单击会改为打开主窗口
- 在 Windows 11 上，将**设置 > 托盘窗口的打开位置**设为**快速设置**（默认为**托盘图标**）时，托盘图标会打开主窗口，而浮出窗口会随快速设置一起打开，显示在那里的面板上方，并随之关闭。在那里使用它不会关闭这些面板。如果屏幕高度不够，它会在面板左侧打开。选择**不打开**时，不会打开浮出窗口，托盘图标会打开主窗口。
- **右键单击**打开菜单：**打开 A2DP Windows Bridge**、前 10 台设备，按名称显示（LE Audio 条目带有“(LE Audio)”标记；正在串流的带勾选标记；单击即可连接该设备）、**断开连接**和**退出**。菜单会立即打开，无需启动窗口
- 工具提示会显示 A2DPWB 处于空闲还是已连接

**设置 > 最小化到系统托盘**开启时（默认），最小化或关闭窗口只是将其隐藏到托盘，串流继续进行。关闭该项时，窗口会最小化到任务栏，关闭窗口则会退出 A2DPWB。托盘菜单中的**退出**或**设置 > 退出 A2DP Windows Bridge** 会停止串流、释放适配器并完全关闭 A2DPWB。

## 随 Windows 启动 {#autostart}

**设置 > 随 Windows 启动**会在你登录时启动 A2DPWB。开启**在托盘中启动**时，它在后台启动：只显示托盘图标，窗口可从托盘打开。关闭该项时（默认），会打开主窗口。它对应 `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run` 下名为 `A2DPWB` 的值，数据为 `"<folder>\a2dpwb-core.exe"`，开启**在托盘中启动**时后面加上 `--background`。如需手动关闭，删除该值即可。在 v1 上覆盖安装 v2 时，**在托盘中启动**会被开启，因为 v1 总是在托盘中启动。

## CLI 模式

`a2dpwb-core.exe --cli` 在控制台中串流，使用与窗口相同的核心。请先退出 A2DPWB（托盘 > **退出**）：同一时间只能有一个程序使用适配器。CLI 不读取已保存设备的设置；所有设置都通过选项指定。

### 基本用法

```bash
# Auto-select best codec
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF
```

按 Ctrl+C 停止串流。CLI 会输出状态、编解码器和比特率，并在结束时输出已发送和已丢弃的数据包数。

### 选择编解码器

```bash
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac      # LDAC
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxhd    # aptX HD
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxll    # aptX Low Latency
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptx      # aptX
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aac       # AAC
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c sbc       # SBC
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c lhdcv5    # LHDC V5
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c opus      # Opus (experimental; 48 kHz, 256 kbps)
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c opus05    # PipeWire's Opus 05 (experimental; to PipeWire sinks)
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxad    # aptX Adaptive (48 kHz; --rate 96000 for 96 kHz)
```

自动选择的优先级：LHDC V5 > LDAC > aptX Adaptive > Opus（实验性）> aptX HD > aptX > aptX LL > AAC > SBC XQ > SBC（FastStream 和 Opus 05 均为实验性，仅在明确选择时使用）

如果耳机不提供所请求的编解码器，CLI 会停止并显示说明原因的错误；使用 `-c auto`（默认）即可采用耳机提供的最佳编解码器，或使用 `--fallback` 像应用那样改用耳机提供的最佳编解码器，而不是所请求的编解码器——请参阅 [aptX 系列与 aptX Adaptive](#aptx-compatibility)。`--no-experimental` 从不使用实验性编解码器（aptX HD、aptX LL、Opus、Opus 05、FastStream）；应用则始终使用它们。

### 音质

```bash
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q hq   # High, 990 kbps (default)
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q sq   # Medium, 660 kbps
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -q mq   # Low, 330 kbps

# LHDC V5: hq 1000 / mhq 900 / sq 500 / mq 400 kbps
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c lhdcv5 -q sq   # Medium, 500 kbps

# aptX Adaptive: hq 427 / ll 265 kbps
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxad -q ll   # Low Latency
```

其他编解码器没有音质选择：它们以 `hq` 运行，即耳机接受的最高比特率（aptX、aptX HD、aptX LL 和 FastStream 的比特率由编解码器固定）。编解码器没有的级别（LHDC V5 以外的任何编解码器的 `mhq`、aptX Adaptive 的 `sq` / `mq`、aptX Adaptive 以外的任何编解码器的 `ll`）以 `hq` 运行。

### ABR（自适应比特率） {#abr}

```bash
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c ldac -a
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c lhdcv5 -a
a2dpwb-core.exe --cli -d AA:BB:CC:DD:EE:FF -c aptxad -a
```

ABR 会在 Bluetooth 连接不稳定时自动降低比特率，并在状况改善后提高比特率。LDAC 在其各音质模式之间切换；LHDC V5 遵循 Android 的策略，保持在 160 到 400 kbps 之间；aptX Adaptive 在高音质下于其各级别之间逐级切换（请参阅 [aptX Adaptive](#aptx-adaptive)）。在窗口中，ABR 位于编解码器的设置中（**编解码器**页面卡片上的 **...**）。

### 设备发现

```bash
# Nearby devices, found with the USB adapter (10 seconds; --scan 20 for longer)
a2dpwb-core.exe --cli --scan
```

请先让耳机进入配对模式。

| `-l` | 列出与 Windows 配对的 Bluetooth 设备并退出 |

| `--remote-sink <host[:port]\|auto>` | 显示对端接收器收到的内容；未指定 `-d` 时，向该接收器串流（请参阅[对端接收器测试](#receiver)） |

## 捕获模式 {#capture-modes}

A2DPWB 支持三种音频捕获模式，分别录制音频路径中的不同位置：

| 模式 | 录制内容 |
|:-----|:----------------|
| 系统环回 | Windows 默认输出设备播放的内容：所有应用混合后的声音 |
| 虚拟设备 | 应用播放到所选设备（如 VB-CABLE）的内容 |
| 应用程序 | 仅某一个应用（及其子进程）播放的内容，且是经过该应用自身处理之后的声音。需要 Windows 11 或 Windows 10 版本 2004（内部版本 19041）及更高版本 |

**音频设备**页面的**输出源**下也有相同的说明。新设备使用系统环回捕获，无需安装任何其他软件即可使用；如需虚拟设备或应用程序，请在那里为其选择。

系统环回只是复制音频，不会把声音从默认输出设备上拿走，因此声音也会在该设备（扬声器、有线耳机、HDMI 电视等）上播放。如果只想在 Bluetooth 耳机上听到，请使用 VB-CABLE 等虚拟设备。

在开发者模式下开启**开发者 > 应用设置 > 使用音量合成器**后，**连接期间将 Windows 默认输出设备静音**（在**音量合成器**页面中；默认关闭）会在串流期间将该设备静音，并在串流停止时取消静音；测试音以外的所有捕获来源都适用。这不会影响 A2DPWB 获取的音频。此时 Windows 的静音键会改为让耳机静音（发送静音；再按一次恢复播放），而该设备保持静音；音量键在 Windows 中本来也会取消静音，此时则让该设备保持静音、耳机继续播放。对于 LE Audio 设备，静音键只会让该设备保持静音。原本已静音的设备保持静音；如果 A2DPWB 意外退出，设备会保持静音：请在 Windows 中取消静音。关闭开发者模式时，无论此设置如何，都不会静音。

开启该开关后，**音量合成器**页面和浮出窗口可以设置各应用的音量，无论是否使用该静音。输出静音时它们也可使用（Windows 合成器此时可能中断声音）。如果 Windows 默认输出是虚拟设备，将其静音可能使串流也没有声音：此时请关闭静音。

在虚拟设备模式下，**连接期间设为 Windows 默认输出设备**会在串流期间将所选设备设为 Windows 默认输出设备，这样无需更改 Windows 设置，应用就会播放到该设备。停止串流时，A2DPWB 会切换回之前的默认设备。

- **音频设备**列表中只显示 A2DPWB 识别为虚拟音频设备的设备。如果没有这样的设备，**音频设备**界面会说明为何需要虚拟设备，并提供**下载 VB-Cable**。
- 默认通信设备（通话类应用使用的设备）不会被更改。
- 某些应用在重新启动之前，仍会继续在之前的设备上播放。
- 如果 A2DPWB 意外退出，默认设备不会被切换回去。请在 Windows 声音设置中更改。

### 应用程序模式 {#application-mode}

应用程序模式发送某一个应用的音频，例如音乐播放器、浏览器或音效应用。在**应用**列表中选择该应用。列表显示当前正在播放音频的应用；如果找不到你的应用，请先在其中开始播放，然后单击**刷新**。应用的子进程也包含在内，因此在独立进程中播放音频的浏览器也能正常工作。

- 应用不必正在运行。A2DPWB 仍会连接耳机，并在应用启动后开始发送。如果应用在串流期间退出，A2DPWB 会保持连接，并在应用重新启动后重新捕获它。
- 应用仍会在其自身的输出设备上播放。如果只想在耳机上听到，请将该输出设备静音（其主音量）：这不会影响 A2DPWB 捕获的内容。但不要在 Windows 音量合成器中将该应用静音，否则耳机也会没有声音。
- 应用在 Windows 音量合成器中的滑块会改变发送到耳机（以及其输出设备上）的音量。主音量和音量键不会改变发送的音频；当 **Windows 音量同步**开启时，它们改为调节耳机的音量（请参阅[音量](#volume)）。
- Windows 会将音频转换为 A2DPWB 请求的采样率，因此声音设置中的设备格式不会对其造成限制。
- 在 Windows 10 版本 2004（内部版本 19041）之前的版本上，Windows 不支持按应用捕获。此时连接设为“应用程序”捕获的设备会显示错误，提示选择其他输出源。

### 音量 {#volume}

串流期间，如果耳机支持 AVRCP 绝对音量，主页和托盘浮出窗口会显示**音量**滑块。它直接设置耳机本身的音量，因此发送的音频保持完整的分辨率。旁边的扬声器图标可静音（耳机音量设为 0）和取消静音（恢复之前的音量）。音量为 0 时，无论是如何设置的（扬声器图标、滑块、Windows 或耳机按键），A2DPWB 都会发送静音，因为很多耳机在最低音量下仍会发出微弱的声音。该滑块也会跟随耳机上的音量按键和触控操作。

**Windows 音量同步**（在**音频设备**页面，适用于所有设备；默认开启）会在串流期间将某个 Windows 音量与耳机音量合为一个音量。同步的是 A2DPWB 捕获的设备的 Windows 音量：系统环回和应用程序模式下为默认输出设备，虚拟设备模式下为所选设备。关闭时，Windows 音量与耳机音量相互独立。

- 耳机的音量按键和手势以及**音量**滑块会调节同步的 Windows 音量，而声音设置中该设备的滑块会调节耳机的音量。
- 音量键和 Windows 音量浮出控件始终作用于默认输出设备，因此只有当默认输出设备就是同步的设备时，它们才会改变耳机音量（通常始终如此，但在未开启**连接期间设为 Windows 默认输出设备**的虚拟设备模式下除外）。
- 开始串流时，耳机音量会采用 Windows 音量；停止串流时，设备会恢复到之前的音量。
- 音频是在应用 Windows 音量之前被捕获的，因此只会在耳机上衰减一次。如果同步的音量也会改变捕获到的音频，音量就会被应用两次：此时请关闭同步（请参阅[系统级音效应用](#effects-apps)）。
- 静音不会同步：将输出设备静音会让 PC 不发声，但不会让耳机静音。

早期版本允许设备跟随另一个输出设备的音量（在开发者模式下）；该选择已不再使用。

A2DPWB 会保存每台音频设备自己的音量，并在其连接后、发送任何音频之前立即重新设置，因此一台设备的音量不会带到另一台设备上。

### 耳机按键 {#headphone-buttons}

串流期间，耳机上的播放/暂停、下一曲和上一曲控制（按键或触控手势，例如 WH-1000XM4 上的双击）可控制 PC 上的播放：A2DPWB 将它们作为媒体键传递给 Windows，由 Windows 媒体控件中显示的应用（Spotify、浏览器、媒体播放器等）接收。停止也会被传递。

- 播放和暂停都作为 Windows 的播放/暂停键处理，因此即使耳机所认为的状态已过时，每次轻点也总会在播放和暂停之间切换。
- A2DPWB 会告诉耳机当前是否在播放音频（依据是否有可捕获的音频），因此摘下时会暂停的耳机也能发送正确的命令。
- 快进 / 快退（长按按键）没有对应的 Windows 媒体键，会被忽略。
- 音量手势会改变耳机自身的音量；开启 **Windows 音量同步**时，同步的 Windows 音量也会随之变化（请参阅[音量](#volume)）。
- 可通过**音频设备 > 用音频设备的按钮控制播放**为每台设备关闭此功能，例如另一个程序已经响应媒体键、导致操作被执行两次时。

此功能需要耳机支持 AVRCP，几乎所有耳机都支持。如果不支持，串流仍可照常进行，只是按键不起作用。

### 系统级音效应用 {#effects-apps}

系统级音效应用（均衡器、音效增强、虚拟环绕声应用等）通常会安装自己的虚拟输出设备。其他应用播放到该设备；音效应用处理音频后，将结果播放到你在音效应用中选择的输出设备。在 A2DPWB 中选择哪种模式，决定了耳机是否能获得音效：

| 设置 | 到达耳机的内容 |
|:--------|:----------------------------|
| 虚拟设备：音效应用自身的虚拟设备 | 音效处理**之前**的音频：应用送入音效应用的内容 |
| 应用程序：音效应用 | 音效处理**之后**的音频：音效应用播放的内容（推荐） |
| 虚拟设备：音效应用的输出设备（例如将 VB-CABLE 设为其输出） | 音效处理之后的音频（适用于不支持应用程序模式的 Windows 版本） |

在应用程序模式下，音效应用的输出设备可以是任意设备：A2DPWB 获取的是应用播放的内容，而不是设备播放的内容，因此该设备只是音频的去处。为了不让 PC 同时发声，请选择没人收听的输出（例如显示器的 HDMI 音频），或将该设备的主音量静音。VB-CABLE 这样的虚拟设备也可以作为静默的输出目标，但并非必需。该设备必须已启用且已连接。

如果音效应用自身的虚拟设备是 Windows 默认输出设备，其音量也会降低音效应用接收到的音频。此时若 **Windows 音量同步**开启，音量变化会被应用两次（在音效应用的输入端和耳机上）。请将其关闭，并使用耳机的音量或**音量**滑块。

#### 为什么 A2DPWB 没有自己的虚拟输出设备 {#no-virtual-device}

要在 Windows 输出设备列表中出现一个可供音效应用直接选择的 Bluetooth 耳机项，就需要内核模式音频驱动。A2DPWB 不包含这样的驱动：

- 编写和维护内核音频驱动工作量很大，其中的错误可能导致 Windows 崩溃（蓝屏）。
- Windows 10 和 11 只加载经过 Microsoft 签名的驱动。获得该签名需要 EV 代码签名证书（每年数百美元）和 Microsoft 合作伙伴中心帐户，通常需以公司名义注册。
- 绕过签名的唯一方法是 Windows 测试签名模式，它会降低系统安全性，并导致部分软件（例如带反作弊的游戏）无法正常运行。A2DPWB 不会依赖它。

应用程序模式，或 VB-CABLE 等免费虚拟设备，可以满足相同的用途。

- Windows 没有用于更改默认设备的公开 API。A2DPWB 与其他音频切换工具一样，使用未公开的 IPolicyConfig 接口（Windows 10 和 11）。

{: .warning }
系统环回和虚拟设备使用 WASAPI 共享模式：采样率为“自动”时（包括自动选择），A2DPWB 会请求 48 kHz（耳机未列出 48 kHz 时，请求其列出的最佳采样率），由 WASAPI 将设备的**默认格式**重采样为该采样率。如需以 96 kHz 使用 LDAC，请在编解码器的设置中选择 96 kHz；无需更改**声音设置 > 设备属性 > 高级**中的**默认格式**。

## 编解码器比较

| 编解码器 | 适合 | 取舍 |
|:------|:---------|:----------|
| LHDC V5 | 最高的比特率和采样率（最高 1000 kbps、192 kHz） | 设备很少；需要稳定的连接 |
| LDAC (HQ) | 许多 Sony 和面向 Android 的设备上的最高音质 | 延迟较高，需要稳定的连接 |
| LDAC (ABR) | 音质 + 稳定性 | 比特率随连接状况波动 |
| aptX Adaptive | 高音质并带低延迟模式，适用于基于 Qualcomm 的设备 | 比特率随链路变化 |
| Opus 🧪 | 高效，256 kbps 下音质良好 | 接收端很少（Android 的 A2DP Opus、PipeWire） |
| aptX HD | 高音质，设备支持更广 | 固定 576 kbps |
| aptX | aptX 设备支持最广 | 16-bit，352/384 kbps |
| aptX LL | 游戏、视频（低延迟） | 音质较低（16-bit） |
| AAC | Apple 设备，效率高 | 音质中等 |
| SBC XQ | 在 SBC 允许的任何设备上都远好于 SBC | 需要双声道和 bitpool ≥ 29；约 385-552 kbps |
| SBC | 兼容性最佳 | 音质最低 |

**编解码器**页面在每张编解码器卡片上以三个指标条显示相同的比较。

## aptX 系列与 aptX Adaptive {#aptx-compatibility}

A2DPWB 支持三种使用 [libopenaptx](https://github.com/pali/libopenaptx) 编码的 aptX 编解码器，以及使用 [AKS-Logic/aptx-adaptive-linux](https://github.com/AKS-Logic/aptx-adaptive-linux) 编码器编码的 aptX Adaptive。

{: .warning }
**aptX HD 和 aptX Low Latency 为实验性功能。** 它们参照 Android / PipeWire 的实现，并通过了编码/解码往返测试，但尚未在真实耳机上验证。

{: .note }
**只需要经典 aptX？** Windows 10 的内置 Bluetooth 堆栈已经支持经典 aptX（不含 aptX HD、aptX LL 和 aptX Adaptive），因此无需 A2DPWB。A2DPWB 主要用于 LDAC、aptX HD 和 aptX Low Latency。

| 编解码器 | Vendor ID / Codec ID | RTP 标头 | 状态 |
|:------|:---------------------|:-----------|:-------|
| aptX Adaptive | 0x000000D7 / 0x00AD | 有 | 支持（265-427 kbps，48 / 96 kHz，24-bit） |
| aptX HD | 0x000000D7 / 0x0024 | 有 | 支持（576 kbps，24-bit 输入） |
| aptX | 0x0000004F / 0x0001 | 无 | 支持（44.1/48 kHz 下 352/384 kbps） |
| aptX Low Latency | 0x0000000A 或 0x000000D7 / 0x0002 | 无 | 支持（352 kbps） |

### aptX Adaptive {#aptx-adaptive}

{: .note }
**aptX Adaptive 已在 48 kHz 下用真实耳机确认：** 有用户在 2.0.2-beta.6 上将它串流到 EarFun Air Pro 4+，没有断音或卡顿，与经典 aptX 一样稳定（[#86](https://github.com/SeiyaFunaokaJP/A2DP-Windows-Bridge/issues/86)）。它还通过了单元测试、上游的逐位一致性测试套件，以及针对虚拟 Bluetooth 接收端的端到端测试（`tools/emu`，检查 RTP 标头、数据包大小和帧类型；由于没有开源解码器，不对音频进行解码）。上游报告它在 Linux / PipeWire 上可用于 Bose QuietComfort Ultra（第 1 代）和 B&W Px7 S2e，48 kHz，高音质和低延迟均可。96 kHz（高，646 kbps）也已用真实耳机确认（[#86](https://github.com/SeiyaFunaokaJP/A2DP-Windows-Bridge/issues/86)）：在编解码器的设置中选择它时（CLI `--rate 96000`），如果耳机是列出 96 kHz 的 R2 接收端（设置只在这种情况下提供它），就会使用 96 kHz，低延迟下从不使用。“自动”（包括自动选择）以 48 kHz 串流。[欢迎反馈](https://github.com/SeiyaFunaokaJP/A2DP-Windows-Bridge/issues/11)。

编码器是 [AKS-Logic/aptx-adaptive-linux](https://github.com/AKS-Logic/aptx-adaptive-linux) 的纯 Rust aptX Adaptive 编码器（MIT）。上游称其为净室重新实现，其中的数值表是根据合法获得的 Qualcomm 已出货二进制文件和空中抓包重建的；不包含任何 Qualcomm 代码、SDK 或二进制文件（请参阅[许可证](../licenses)）。

- **选择方式**：耳机既不提供 LHDC V5 也不提供 LDAC 时，“自动”会选择它。也可以在**编解码器**页面选择 **aptX Adaptive**，或使用 `-c aptxad`。
- **格式**：48 kHz 立体声、24-bit；选择 96 kHz 时，对列出 96 kHz 的设备（aptX Adaptive R2）以高音质使用 96 kHz；请求 44.1 kHz 时以 48 kHz 捕获。
- **耳机**：R1 接收端（无能力扩展，例如 B&W Px7 S2e）和 R2 接收端（R2 比特流）。

| 音质（**...** / `-q`） | R1 接收端 | R2 接收端 | 数据包 |
|:-------------------------|:---------|:---------|:--------|
| 高（`hq`） | 427 kbps | 427 kbps | 12 ms，656 字节 |
| 低延迟（`ll`） | 265 kbps | 270 kbps | 10 ms，348 字节 |

`ll` 仅供 aptX Adaptive 使用；其他编解码器将其视为高。标准和移动级别（R1 364 / 318 kbps，R2 270 / 204 kbps）不再作为音质提供：以其中之一保存的设备，以及 `-q sq` / `-q mq`，均以高运行；ABR 仍会在它们之间逐级切换。

**ABR**（编解码器设置中的 **ABR**，CLI `-a`）：在高音质下，当发送队列中有 3 个或更多数据包时，比特率降低一级（先降到标准，再降到移动，不再更低），最多约每 0.5 秒一次；当队列中最多只有一个数据包持续约 3 秒后，再提高一级（最高到高）。低延迟没有 ABR。

### 不存在从 aptX Adaptive 到 aptX 的“回退”

A2DPWB 连接时，耳机会通告一个**编解码器列表**（AVDTP 流端点）。A2DPWB 从该列表中选择一种编解码器。aptX Adaptive 和经典 aptX 是列表中各自独立的项，因此在编解码器内部不存在从一方“回退”到另一方的情况：

- **耳机同时列出了经典 aptX**——许多 aptX Adaptive 耳机都是如此，因为 Qualcomm 宣传 aptX Adaptive 向下兼容 aptX / aptX HD。“自动”会选择 aptX Adaptive（高于 aptX HD 和 aptX）；经典 aptX 在您选择它时使用，它是耳机列表中独立的一种编解码器，而不是 aptX Adaptive 的降级模式。
- **耳机只列出了 aptX Adaptive**（没有经典 aptX、aptX HD 或 aptX LL）——选择 aptX 时会回退到耳机提供的最佳编解码器（按**编解码器**页面上该设备的顺序），通常就是 aptX Adaptive 本身。

自动选择的优先级：LHDC V5 > LDAC > aptX Adaptive > Opus（实验性）> aptX HD > aptX > aptX LL > AAC > SBC XQ > SBC（FastStream 和 Opus 05 均为实验性，仅在明确选择时使用）

### 明确指定的编解码器不可用 {#codec-fallback}

当你请求了耳机未列出的特定编解码器时：

| 位置 | 行为 |
|:------|:---------|
| 应用（**编解码器**，自动选择关闭） | 与“自动”一样，使用该设备顺序中（除非你拖动过卡片，否则为“自动”的优先级顺序）耳机提供的第一个编解码器连接（选择 Opus、耳机提供 aptX Adaptive、aptX、AAC 和 SBC 时：使用 aptX Adaptive，而不是排在 Opus 之下的 aptX；把 SBC XQ 拖到最前时：使用 SBC XQ），编解码器标签会在几秒内显示改用了哪种编解码器以及原因。从不尝试耳机不提供的编解码器。在**编解码器**页面上，单击耳机上次连接时未提供的卡片会改为选择该编解码器，而之前选择的、耳机不提供的编解码器会将实际使用的编解码器显示为已选择。 |
| CLI（`-c <codec>`） | 以错误停止（“设备不支持 ...”）；如果你请求的是 aptX、aptX HD 或 aptX LL，而耳机只提供 aptX Adaptive，消息中会说明这一点。添加 `--fallback` 可像应用一样回退，或使用 `-c auto`。 |

早期版本使用的是**此编解码器不可用时使用其他受支持的编解码器**选项；现在回退始终开启。部分 2.0.2 预发布版本采用的是所选编解码器之下的下一个编解码器，而不是最佳编解码器。

### 耳机同时连接其他设备时缺少编解码器 {#sep-in-use}

耳机通过流端点（SEP）提供各个编解码器。在双设备（多点）连接时，正在向手机或 PC 串流的端点会被报告为**正在使用**，在该串流停止之前无法使用其编解码器。有些耳机还只在仅连接一台设备时才提供高解析度编解码器（LDAC、L2HC 等）。此时 A2DPWB 会在日志中记录：

```
remote SEP 6: sink audio, IN USE (codec not queried)
remote SEPs in use by another connection: 1 of 6 audio sink SEP(s); ...
capability discovery complete (LDAC=false ... , 1 of 6 audio sink SEP(s) in use)
```

并且错误消息会说明端点正被其他设备使用。请断开耳机与手机 / PC 的连接（或在耳机的应用中关闭双设备连接），然后重新连接。如果 PC 的内置 Bluetooth 仍与耳机配对，也算作其他设备。

Sony 耳机（例如 WH-1000XM4）在开启**同时连接 2 台设备**（多点连接）时不提供 LDAC：请在 Sony Sound Connect 应用中将其关闭，然后重新连接。部分型号（例如 WH-1000XM6）支持 LDAC 与多点连接同时使用。

耳机自带的应用（电量、降噪、EQ）需要一条到耳机的独立链路，来自手机或这台电脑的内置蓝牙。应用连接期间，耳机处于双设备连接状态，A2DPWB 切换编码可能变慢或失败。切换编码前请断开手机或关闭该应用。[EncoDeck](../works-with) 改为通过 A2DPWB 自己的链路控制耳机，不会增加第二条连接。

### 采样率

aptX、aptX HD 和 aptX LL 只支持 44.1 kHz 和 48 kHz（aptX Adaptive 为 48 kHz；选择 96 kHz 且耳机列出时为 96 kHz）。A2DPWB 会从耳机通告的采样率中选择一个（“自动”时为 48 kHz，没有则为 44.1 kHz），并由 WASAPI 对捕获的音频进行重采样。使用 aptX 时无需更改 Windows 声音设置。

### 查看耳机提供的编解码器

1. 连接耳机。
2. 打开**诊断**，在日志筛选框中输入 `remote`。

相同的内容也会写入配置文件夹中的日志文件（`%APPDATA%\A2DPWB\logs\a2dpwb-core.<date>.log`；不做隐藏处理，附加到报告之前请先检查）；在 CLI 模式下则输出到控制台。功能发现相关的日志行会准确显示耳机列出了哪些编解码器：

```
remote supports aptX (SEID ..., [...])
remote supports aptX Adaptive (SEID ..., [...])
remote vendor codec 0x........./0x.... (SEID ...) - unsupported
capability discovery complete (LDAC=false aptX HD=false aptX LL=false aptX=true aptX Adaptive=true SBC=true SBC XQ=true AAC=true LHDC V5=false Opus=false Opus 05=false FastStream=false)
```

- `aptX=true`——可以使用经典 aptX（即使同时有 `aptX Adaptive=true`）；“自动”会使用它。
- `aptX=false`、`aptX HD=false`、`aptX LL=false` 且 `aptX Adaptive=true`——耳机只提供 aptX Adaptive；请选择 aptX Adaptive，或使用“自动”、AAC 或 SBC。
- `aptX Adaptive=true [not usable]`——耳机提供的 aptX Adaptive 不支持 A2DPWB 所需的 48 kHz 立体声。
- `remote vendor codec ... - unsupported`——A2DPWB 未实现的其他厂商编解码器。

## 最大媒体数据包大小（每台设备） {#max-packet}

每台设备的**最大媒体数据包大小**（**开发者**页面，每台已保存的设备一个字段；CLI：`--max-packet <bytes>`）设置每个 Bluetooth 数据包中音频数据的上限，范围为 679 到 1679 字节，这样需要不同值的音频设备可以各自使用自己的设置。“开发者”页面在开发者模式（**设置 > 开发者模式**）下显示；大多数用户从不需要它。音频设备自身的上限（MTU）也始终有效；A2DPWB 使用两者中较小的值。更改从下次连接时生效。它以前是配置文件的设置（位于**高级**下）：设备会沿用其保留下来的配置文件的值（请参阅[编解码器](#codecs)）；1.1 之前的 v1 保存的配置文件会沿用当时全局设置的值。

**推荐使用 1023（默认）。** 它正好容纳一个 Bluetooth 基带数据包（3-DH5）。更大的值只能节省 1-2% 的开销，而每丢失一个数据包会损失更多音频。679 正好容纳一个 2-DH5 数据包，也是 LDAC 接受的最小值。

## 验证媒体流（a2dpwb_decode） {#verify-stream}

大多数耳机无法显示正在使用的编解码器。**诊断 > 开始 HCI 捕获** / **停止 HCI 捕获**会记录一份 HCI 数据包日志（配置文件夹中的 `hci_<date>_<time>.pklg`），包含编解码器协商和发送的每个媒体数据包。在 LDAC 990 kbps 下，它每小时大约增长 0.5 GB，因此请只在需要时进行捕获。在 CLI 模式下，`--hci-capture <file.pklg>` 会记录整个运行过程。

可以在连接前开始捕获，也可以在串流过程中开始。如果在连接期间开始捕获，A2DPWB 会先写入它记住的连接建立数据包（L2CAP 信道建立和 AVDTP 信令，包括编解码器协商），因此该文件仍然可以分析。“诊断”会在记录期间和停止后显示文件路径。

可以用 Wireshark 打开捕获文件，或使用开发者工具 `a2dpwb_decode`（需从源代码构建，请参阅[构建](../building)）进行检查：

```
a2dpwb_decode "%APPDATA%\A2DPWB\hci_20260925_120000.pklg" -o C:\temp\check
```

该工具会跟踪 AVDTP 信令（SET_CONFIGURATION / RECONFIGURE 以及耳机是否接受），提取 A2DPWB 发送的媒体数据包，并对照协商的配置进行检查：

| 编解码器 | 检查内容 | 输出 |
|:------|:----------------|:-------|
| SBC、SBC XQ、FastStream、AAC、aptX、aptX HD、aptX LL、Opus、Opus 05 | 使用参考解码器完整解码；帧参数与配置是否一致；媒体负载标头中的帧数 | 可供试听的 `<prefix>.<n>.<codec>.wav` |
| LDAC | 仅检查帧头（同步字、采样率、声道模式、帧长度）、帧数和比特率。不存在开源的 LDAC 解码器 | 仅报告 |
| LHDC V5 | 仅检查帧头（媒体负载标头中的帧数、序列号）和比特率。不存在开源解码器 | 仅报告 |
| aptX Adaptive | 仅检查其自身的 RTP 标头（采样计数时间戳、延迟模式）和编解码器数据包标头。不存在开源解码器 | 仅报告 |

`a2dpwb_decode --le-audio` 对 LE Audio 捕获（通过 CIS 传输的 LC3）进行同样的检查。

对于每个流，它还会报告 RTP 序列号的间断、RTP 时间戳的推进速度、比特率，以及 Bluetooth 控制器报告已完成的 ACL 数据包数量。最后一行为 `RESULT: OK` 或 `RESULT: PROBLEMS FOUND`（退出代码为 0 或 1）。

{: .note }
这可以证明 A2DPWB 发送了什么，以及这些内容对于协商的编解码器是否有效。由于接收端只能解码协商好的编解码器，如果耳机播放的声音正常，同时报告也没有问题，就足以有力地证明该编解码器确实在使用中。

## 链路质量与 AFH {#link-quality}

**诊断 > 链路质量**会显示串流期间 A2DPWB 发送的内容：实际比特率、已发送的数据包、发送前丢弃的数据包（它们在发送队列中等待过久：无线链路跟不上）、捕获时丢弃的音频（PC 跟不上）、发送队列、无线占用时间，以及**信号（与理想值之差）**：连接的 RSSI（相对于控制器的理想接收范围，0 = 正常，负值 = 太弱；并非绝对电平；为负值时另附实际电平的上限，单位 dBm），以及链路在 79 个 Bluetooth 信道中的多少个信道上跳频（AFH）。主页和托盘浮出窗口会将其概括为“良好”、“一般”或“较差”；链路正常但 PC 丢弃了音频时显示“电脑繁忙”。

Bluetooth 会自行避开繁忙的信道（AFH），但它只能通过错误来了解 Wi-Fi 的存在。A2DPWB 还会在每次连接时告诉其控制器应避开哪些信道（AFH 主机信道分类）：

| AFH | |
|:--|:--|
| 自动（默认） | 仅本 PC 所连接的 2.4 GHz Wi-Fi 信道（连接期间每 30 秒重新检查一次）。PC 未使用 2.4 GHz Wi-Fi 时（未连接、使用 5 GHz，或有线连接）不指定任何信道。它只读取信道编号，因此不需要位置权限；编号为 1 到 14 的 6 GHz 信道会被视为 2.4 GHz |
| 关 | 不指定：由控制器自行决定 |
| 手动，例如 `6,11` | 指定的 Wi-Fi 信道（1 到 14） |

对于 PC 只是能接收到的网络，“自动”会交给控制器自身的 AFH 处理：避开邻居的繁忙信道会从跳频中拿走 22 MHz，反而可能让链路变差。如果仍想避开这样的信道，请以“手动”方式输入。

始终至少保留 20 个 Bluetooth 信道可用。可以在**适配器**页面、`settings.json`（配置文件夹中）的 `"afh"`，或 CLI 模式下的 `--afh` 进行设置。无线一行会显示正在避开哪些 Wi-Fi 信道。是否有帮助取决于环境：请用对端接收器测试进行测量。

## 对端接收器测试（tools/linux_sink） {#receiver}

链路质量显示的是 A2DPWB 发送的内容。要查看实际到达的内容，请在另一台运行 Linux 的 PC 上运行 `tools/linux_sink/a2dpwb_sink.py`。它直接驱动该 PC 上的普通 Bluetooth 适配器（内置适配器即可），通过 HCI user channel 使用 Bumble，作为支持包括 LDAC 在内所有编解码器的 A2DP 接收端，测量到达的每个媒体数据包，并通过网络提供统计数据：

将 `tools/linux_sink` 文件夹复制到 Linux PC 上（只需这个文件夹），然后运行：

```bash
sh setup.sh      # once: decoder libraries, Python environment (Ubuntu / Debian, Python 3.11+)
sudo sh run.sh   # start the receiver (root: it takes the Bluetooth adapter)
```

在 Windows PC 上退出 A2DPWB（托盘 > **退出**），然后运行：

```bash
a2dpwb-core.exe --cli --remote-sink auto -c ldac --test-tone
```

`--remote-sink auto` 会在本地网络中查找接收器，向其 Bluetooth 适配器串流（除非 `-d` 指定了其他设备），并每 5 秒以及结束时输出接收器的统计数据：比特率、丢失和迟到的数据包（RTP 序列号）、抖动和间隔、模拟播放缓冲区中的断音和跳过、流 / 解码错误，以及接收端的 RSSI（相对于其理想接收范围：0 = 正常，负值 = 太弱）。不加 `--test-tone` 时发送系统音频。`--remote-sink <host[:port]>` 可直接指定接收器，而不进行查找。

同样的测试也可以在窗口中进行：开启**设置 > 开发者模式**后，打开**开发者 > 对端接收器测试**。将**接收器**留空即可在本地网络中查找接收器（或输入其地址），**连接**会连接到其统计数据；选择编解码器、其设置、音源（**测试音**或**系统音频**），如有需要再选择接收器提供的 L2CAP MTU 和播放缓冲区，然后单击**开始**。它会逐步检查，并将本 PC 发送的内容与接收器统计的内容并排显示。无需先退出任何程序：窗口使用正在运行的 A2DPWB。

双方都从流的第一个数据包开始计数，因此可以比较发送和接收的数据包数：两者应当相等。Bluetooth 会在控制器内部重传丢失的无线数据包，而 A2DPWB 在链路保持连接期间不会放弃任何数据包，因此较差的无线链路在接收端会表现为间隔、抖动和断音，而不是丢包；当链路跟不上时，数据包会在发送端于发送前被丢弃。双方都无法获得重传次数。

工具运行期间，接收端的适配器无法供其自身的 Bluetooth 堆栈使用。发现过程使用 UDP 端口 51201 上的广播，因此两台 PC 必须位于同一网段（否则请输入地址）。所有选项和统计协议请参阅 `tools/linux_sink/README.md`。

## LE Audio（实验性） {#le-audio}

A2DPWB 也可以向 LE Audio 耳机传输音频（BAP 单播，通过连接等时流传输 LC3），并支持耳机音量（VCP）、媒体按键（MCP）、一对耳机的左右两只（CSIP）以及游戏耳机的低延迟模式（GMAP）。此功能为**实验性功能**，按设备选择：只有设备的 LE Audio 条目才会使用它。它只在 Bluetooth 模拟器上测试过，**尚未在真实的 LE Audio 耳机上验证**，可能无法与您的设备配合使用；日常收听请使用传统的 A2DP。

需要：

- 支持**等时通道（ISO）的 Bluetooth 5.2 或更新版本**的 USB Bluetooth 适配器（与 A2DP 一样分配 WinUSB）。不支持 ISO 的适配器会以 “adapter does not support LE Audio (no ISO buffers)” 被拒绝。
- 支持 LE Audio（LC3）的耳机。有些型号需要先在其专用应用中开启 LE Audio。

使用方法：

1. 让耳机进入配对模式，在**音频设备**页面扫描设备。LE Audio 设备带有 **LE Audio** 标记，一对耳机带有 **LE Audio 组** 标记（选择其中任意一只，A2DPWB 会找到另一只）。同时支持 A2DP 的耳机会按类型显示两次。
2. 在**编解码器**页面选择 LE Audio 条目的 LC3 卡片。不能选择编解码器和质量（A2DPWB 会选择耳机接受的最佳 LC3 配置），捕获方式只能使用系统环回和虚拟设备。
3. 其下的 **游戏音频设备低延迟（实验性）** 默认开启：对支持 GMAP 游戏角色的耳机使用更短的 LC3 帧；其他耳机则无论开关都使用媒体配置。

设置中没有 LE Audio 开关。如果 LE 部分干扰了适配器，可在 `settings.json`（**设置 > 设置文件夹**）中写入 `"le_audio_experimental": false`，将其完全关闭。

在 CLI 模式下，`--le-audio -d <地址>` 向 LE Audio 设备传输，`--le-device <地址>` 添加组中的另一台设备（另一只耳机），`--le-scan` 列出附近的 LE Audio 设备，`--le-low-latency` / `--le-preset <名称>` 选择配置（所有 LE 选项见 `a2dpwb-core.exe --cli -h`）。

## 更新 {#updates}

A2DPWB 每天最多检查一次 GitHub Releases（**设置 > 启动时检查更新**；**检查更新时包括预发布版本**还会提示 beta 版本）。有新版本时，会弹出一个对话框，用几行文字介绍新内容（完整说明可通过链接查看），并提供**立即更新**（便携版为**打开下载页面**）和**稍后**；选择**稍后**后，直到下一个版本之前都只在“设置”中提示。“设置”中也会显示提示：

- **安装版**：**立即更新**会下载已签名的更新。音频设备连接期间会等待，直到断开连接后再安装，因此更新永远不会打断音频。随后 A2DPWB 会关闭、安装新版本并自动重新启动。
- **便携版**（或未进行更新签名的构建）：**打开下载页面**会打开发布页面。

## 故障排除

声音断续或卡顿、连接失败，或比特率低于预期：请参阅**[断音与连接问题](wireless)**，其中总结了目前为止的报告最终查明的原因，以及应该首先检查什么。

### 窗口提示核心未运行

窗口需要同一文件夹中的 `a2dpwb-core.exe`，并会自动启动它。“A2DPWB 核心未运行”表示无法启动它：请重新安装 A2DPWB（或重新解压便携版 zip）。“核心版本不同”表示两个程序来自不同的版本：请安装两者的相同版本（安装最新版本即可）。

### 分配或恢复驱动程序失败

- “管理员权限请求已被拒绝”：驱动程序未更改。请再次单击按钮并允许该请求。
- “更改驱动程序失败”：详情请查看**诊断 > 日志**。
- “适配器未恢复为之前的驱动程序”：如果适配器是用 Zadig 设置的，Windows 可能会再次选择 Zadig 的 WinUSB 驱动程序包。请在设备管理器中删除该驱动程序包（适配器 > 卸载设备，并勾选“尝试删除此设备的驱动程序”），然后拔下并重新插入适配器。

### Bluetooth 适配器无响应 {#adapter-no-answer}

如果适配器打开后没有任何回应（不响应 HCI Reset），A2DPWB 会在 5 秒后放弃，再打开一次；如果仍无响应，则显示“Bluetooth 适配器无响应”。请拔下适配器，重新插入后再试（或单击**重新启动 Bluetooth**）。无需重新启动 A2DPWB：启动失败时会释放适配器，每次新的启动都会重新初始化它。

为防止适配器卡住，A2DPWB 在打开适配器时会重置其 USB 管道，在关闭时会发送 HCI Reset。

### 更新后出现配对问题

A2DPWB 使用 SSP（Just Works）和 **General Bonding** 进行配对，并保存链接密钥，这样耳机无需重新配对即可再次连接（v2 会读取 v1 的链接密钥）。如果你曾用较旧的 A2DPWB 版本配对过耳机，且现在无法连接，请在耳机上删除 A2DPWB 的配对信息（清除配对列表的方法请参阅耳机的说明书），然后重新配对。

### 连接超时 {#connection-timeouts}

A2DPWB 会注册 SDP 记录（A2DP Source、AVRCP Controller / Target），以便耳机将其识别为音频源。如果连接尝试超时，半开的连接会被断开，因此可以直接重试，无需重新启动 A2DPWB。请确认耳机已开机、在范围内，并且没有连接到其他设备。

当链路建立后没有传输任何数据，或耳机没有应答时，失败的连接会自动重试（最多 3 次）。如果耳机已不再保留配对信息（被重置，或与其他 PC 配对过），已存储的密钥会被丢弃，并重新进行一次配对。随后错误消息会说明发生了什么：

| 消息 | 含义 |
|:--|:--|
| 设备无应答 | 设备关闭、超出范围或不可连接（新设备：请进入配对模式） |
| 连接已建立但没有传输任何数据 | 无线环境问题：请重试，或调整适配器 / 设备的位置 |
| 设备已应答，但随后主动断开了连接 | 设备当前不接受连接：正在关机、充电或已连接到其他设备 |
| 身份验证失败，重新配对后仍然失败 | 请将设备置于配对模式，或删除其配对列表中的条目，然后重试 |

与耳机的**首次连接**需要配对模式；之后会使用保存的链路密钥自动重新连接。如果耳机已处于配对模式仍然失败，它可能仍连接着手机或其他电脑（包括通过 LE Audio）：请在那边断开连接，如耳机的应用中有该选项则关闭 LE Audio，然后让耳机进入配对模式并重新连接。此时日志会显示 `signaling connection failed (0x66)`（因安全原因被拒绝：耳机保留了之前配对的密钥，例如与这台电脑的 Windows Bluetooth 的配对）或 `(0x67)`（因资源不足被拒绝：正被其他设备占用）。

连接中断后会自动重新连接（最多 10 次）。如果 PC 在串流期间进入睡眠，A2DPWB 会在恢复后重新连接；这些尝试不计入次数。

如果你通过关闭再打开耳机的方式在 PC 和手机之间切换耳机，请关闭**音频设备 > 自动重新连接**。这样断开的连接会保持断开，A2DPWB 会释放 Bluetooth 适配器，使耳机可以连接到手机。要再次连接到 PC，请在主页上单击**连接**。
