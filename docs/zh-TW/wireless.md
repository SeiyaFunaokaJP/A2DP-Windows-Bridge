# 斷音與連線問題
{: .no_toc }

聲音中斷、卡頓或停止，連線建立不起來，或位元率低於預期。本頁整理了這類回報最後查出的原因，讓您在回報之前先檢查常見的原因，並說明若都不是這些原因時應該提供什麼。

## 請先檢查這些 {#checklist}

藍牙與 Wi-Fi、無線滑鼠和鍵盤、耳機接收器，以及房間裡其他每個藍牙無線電共用 2.4 GHz 頻段。USB 介面卡的天線很小，耳塞式耳機的天線更小，而您的頭就在它與 PC 之間。目前為止大多數「連線不佳」的回報，最後都是其中之一；每一項只要一分鐘就能試。錯誤回報表單為每一項都提供了勾選框，請勾選您已經試過的項目。

{: .note }
請一次只做一項，中間聆聽幾分鐘：如果斷音停止，就找到原因了。

### 1. 關閉這台 PC 上的其他藍牙介面卡

當 A2DPWB 透過旁邊的 USB 介面卡串流時，Windows 本身的藍牙（內建介面卡）仍持續發射，兩者共用同一個頻段，且天線往往也在同一區域。它也是耳機在 PC 上的應用程式所連線的地方，這會讓耳機多出第二條連線（請參閱下一項）。請在 A2DPWB 執行期間於裝置管理員中停用內建介面卡，至少在測試時停用。A2DPWB 偵測到另一個使用中的介面卡時，會在首頁顯示提示。

第二個使用中的介面卡，是一位長期測試者指出造成連線不穩與轉碼器切換問題的兩個原因之一。

### 2. 只讓耳機保留一條連線

雙重連線（多點連線）讓耳機能同時連線到手機與 PC。每條連線都會佔用無線電時間，有些耳機還會因此提供較少的轉碼器、拒絕免持連線（因此沒有電量），或在開啟期間為另一個裝置保留一個轉碼器端點。耳機的專用應用程式也算在內：它會保持自己的連線，在手機上或透過這台 PC 的藍牙，即使您只用它來看電量或調等化器。

測試方法：在耳機的應用程式中關閉雙重連線，關閉手機的藍牙，關閉手機與 PC 上的專用應用程式，然後從 A2DPWB 再次連線。

雙重連線是那位測試者指出的另一個原因；中斷專用應用程式的連線之後，轉碼器切換變得順暢許多。曾有一次第一次連線遭到拒絕，原因是耳機仍連線到開著 LE Audio 的手機；也有多款耳塞式耳機在有手機或其應用程式介入時，提供給 A2DPWB 的轉碼器較少或位元率較低。Sony 的 LDAC 在耳機的多點連線開啟時不可用。

### 3. 移動介面卡

- 使用 **USB 2.0 連接埠**，或一條短的 USB 延長線。USB 3 連接埠與線材會在 2.4 GHz 頻段輻射雜訊，正好就在介面卡所在的位置。
- 讓它 **遠離其他無線接收器**：電競滑鼠與鍵盤的接收器、無線耳機的接收器、Wi-Fi 天線。相鄰連接埠上的接收器是造成這種現象的常見原因。
- 讓它 **與耳機之間沒有遮蔽**。PC 放在桌子底下，您和桌子擋在中間，會損失大量訊號。用一條 USB 延長線把介面卡拉到桌面上，比其他任何方法都有效。

在一台沒有 Wi-Fi 介面卡可供 AFH 參考的 PC 上，介面卡旁的電競滑鼠接收器讓連結只能承載約 750 kbps，介面卡並將 79 個通道中多達 46 個標記為不良。距離介面卡一公尺的耳塞式耳機仍顯示訊號微弱，在接近位元率上限時，這已足以每隔幾分鐘就完全無聲一次。

### 4. 讓 2.4 GHz Wi-Fi 遠離連結

請把這台 PC，可能的話連手機和附近的其他裝置，都改用 5 或 6 GHz Wi-Fi。如果 2.4 GHz 必須保持開啟，A2DPWB 會告知介面卡避開這台 PC 所連線的通道（AFH，自動）。當 PC 沒有 Wi-Fi 介面卡、使用有線網路，或連線的頻段與路由器的 2.4 GHz 網路不同時，它看不到該 Wi-Fi：此時請查出路由器的通道（路由器的管理頁面，或手機上的 Wi-Fi 分析 App），若它會跳頻就在路由器上固定下來，然後在 **介面卡 > 避開 Wi-Fi 通道 > 手動** 中輸入，例如 `6` 或 `11`。請參閱 [連線品質與 AFH](usage#link-quality)。

在繁忙的 2.4 GHz 網路上，LDAC 990 kbps 在 5 分鐘內遺失了約 1,700 個封包；把路由器固定在一個通道並以手動 AFH 避開它之後，15 分鐘內只有 33 個。

### 5. 給連結留一些餘裕

藍牙連結在最理想的情況下也只能承載 1 Mbps 多一點；LDAC 990 kbps、LHDC V5 的 900 與 1000 kbps，以及高 bitpool 的 SBC XQ 幾乎沒有留下重新傳送的空間。真無線耳塞式耳機會把音訊從一耳轉送到另一耳，這同樣佔用無線電時間，因此即使連結乾淨，900 kbps 以上對它們也很吃力。

- 試試 **ABR**（自適應位元率；LDAC、LHDC V5、aptX Adaptive，SBC 為自適應 bitpool），或降低一級：LDAC 660、LHDC V5 500、SBC XQ bitpool 29 到 36。
- 檢查改用 **SBC 或 AAC** 時斷音是否仍在。如果仍在，問題就不是位元率。
- 檢查耳機本身：把它與手機配對，在手機上設定相同的轉碼器與位元率，在同一個位置聆聽。如果在那邊也會斷音，限制就在耳機這一側。

在一條只能承載 750 kbps 的連結上，500 kbps 以上的設定都會中斷，而 ABR 則零遺失。在 SBC 能力允許 bitpool 53 的平價耳塞式耳機上，SBC XQ 的 bitpool 超過 36 就沒有聲音。同一副耳機上 LHDC V5 隨機斷音，LDAC 卻穩定。乾淨的連結確實承載得了：一台筆電的內建介面卡以 LDAC 990 kbps 串流 5 分鐘，遺失 0 個封包。

### 6. 更新 A2DPWB

有幾個聽起來像無線電問題的卡頓，其實是應用程式本身。2.0.1 在虛擬線路延遲送達音訊時會以快於即時的速度傳送，耳機聽到的就是一秒有聲、一秒無聲；中斷連線 > 連線之後的串流會一直卡頓，直到重新啟動應用程式；過時的藍牙堆疊在睡眠、長時間使用或多次重新啟動後拒絕連線。這些在目前的版本中都已修正（[更新](usage#updates)）。如果更新後問題消失，就不需要回報。

## 解讀連線品質 {#link-quality}

**診斷 > 連線品質**（以及首頁的圖表）能區分問題出在無線電、PC 還是應用程式。請在問題發生時截圖，並附在回報中。

| 您看到的 | 意義 | 指向 |
|:--|:--|:--|
| **訊號（與理想值之差）** 遠低於 0（約 -25 dB 以下） | 耳機的訊號抵達介面卡時，遠低於介面卡的理想範圍。這不是絕對值：0 為理想，-30 表示低於理想 30 dB，因此 -30 仍可能播放，但毫無餘裕 | 無線電：距離、您的頭與身體、介面卡的擺放位置 |
| **傳送佇列** 滿、**傳送前捨棄的封包** 增加、位元率低於轉碼器的設定 | 封包等待無線電的時間太長；連結目前無法承載這個位元率 | 無線電或干擾，或位元率太高 |
| **跳頻 (AFH)** 跳動，或在封包遺失時停在 79 | 介面卡因通道上的錯誤而將其標記為不良；停在 79 表示它已放棄區分 | 干擾：Wi-Fi、其他接收器、第二個藍牙介面卡 |
| **擷取時捨棄的音訊** 增加，首頁顯示 **電腦忙碌** | PC 沒有及時送出音訊 | PC：負載、擷取裝置、虛擬線路 |
| 一切平穩且沒有數值，卻無聲或卡頓 | 連結沒有問題，PC 上也沒有捨棄任何東西 | 應用程式或耳機的解碼器：請附上診斷套件回報 |

從 PC 看不到接收端的情況。要測量實際抵達的內容，可用 [對端接收器測試](usage#receiver)，由一台 Linux PC 扮演耳機。

## 由耳機決定的事 {#headphones}

有些「它只給我 400 kbps」或「沒有 LDAC」的回報，根本與連結無關：是耳機告知 A2DPWB 它接受哪些轉碼器與位元率，A2DPWB 和 Android 一樣照辦。記錄行 `remote supports ...` 會顯示它們提供了什麼。

- **Huawei FreeBuds** 只有在其 AI Life 應用程式設定為「音質優先」且關閉多裝置連線之後，才會向 PC 提供 LDAC；否則只列出 SBC 與 AAC。自 2.0.2 起，在關閉自動選擇並選擇 LDAC 時，A2DPWB 會自行要求該模式。
- **LHDC V5 耳機** 會公布最高位元率。一副耳機在其應用程式的 96 kHz 模式下列出 400 kbps；在 192 kHz 模式下則為 1000 kbps。OPPO Enco Free4 與 Enco X4 不論應用程式如何設定，向 PC 一律列出 400 kbps 與 48 kHz；2.0.2 會在 LHDC V5 以 ABR 關閉的狀態串流時，透過 OPPO 耳機自己的通訊協定要求 Hi-Res，並為此重新連線一次；尚未在實際耳機上確認。
- **ABR** 會讓 LHDC V5 維持在 400 kbps 以下，與 Android 相同。
- 耳機 **為另一個裝置保留** 的轉碼器，在該裝置連線期間不會出現（[耳機連線到其他裝置時缺少轉碼器](usage#sep-in-use)）。

查看耳機提供了什麼：[檢查耳機提供的轉碼器](usage#codec-fallback)。

## 連線失敗 {#connecting}

首頁上的錯誤會說明發生了什麼事；[連線逾時](usage#connection-timeouts) 中的表格解釋每一則訊息。與無線電有關的情況：

- **裝置沒有回應**（Page Timeout）：未開機、超出範圍、第一次連線時未處於配對模式，或介面卡仍在使用 ROM 韌體。沒有韌體的 Realtek 介面卡掃描不到任何裝置，每次連線都會逾時，或能正常開啟但永遠不會串流；曾有一個韌體檔案其實是存下來的網頁。介面卡畫面會顯示韌體是否已載入。
- **連線已建立，但之後沒有傳輸任何資料**：無線電環境，或耳機正忙於另一個裝置。請再試一次，並移動介面卡。
- **驗證失敗**，或記錄顯示 `signaling connection failed (0x66)`：耳機保留了先前配對的金鑰，通常是這台 PC 自己的 Windows 藍牙。`(0x67)`：耳機正被其他裝置佔用，例如開著 LE Audio 的手機。請中斷其他裝置的連線，在耳機的應用程式中關閉 LE Audio，讓耳機進入配對模式並連線一次；之後的連線會使用儲存的金鑰。
- 中斷連線之後耳機 **無法連線到手機**：2.0.2 在中斷連線時會放開連結；如果您是靠關機再開機把耳機在 PC 與手機之間切換，請關閉 **自動重新連線**。

## 回報最後查出的原因 {#reports}

目前為止所有與無線端有關的回報，依最終查出的原因分組。

| 原因 | 回報 | 例子 |
|:--|:--|:--|
| **環境**：無線電、擺放位置、另一個裝置 | 約三分之一 | 同一通道上的 2.4 GHz Wi-Fi、介面卡旁的電競滑鼠接收器、第二個使用中的藍牙介面卡、雙重連線與執行中的專用應用程式、真無線耳塞式耳機上沒有餘裕的位元率、小型耳塞式耳機的微弱訊號、其實是存下來的網頁的韌體檔案 |
| **耳機**：它們向 PC 提供什麼 | 約四分之一 | 只在 Huawei 的音質模式下才有 LDAC、被耳機自身的模式限制在 400 kbps 的 LHDC V5、透過 OPPO 的通訊協定設定的 Hi-Res、為手機保留的轉碼器 |
| **應用程式**：A2DPWB 的錯誤，皆已修正 | 不到一半 | 使用虛擬線路時音訊以快於即時的速度傳送、中斷連線 > 連線之後卡頓、睡眠或多次重新啟動後過時的藍牙堆疊、中斷連線後仍保留連結、主動連線的耳機被誤判為金鑰錯誤、隱藏了 LDAC 的轉碼器快取、未被辨識的介面卡（某個晶片、某個 USB 類別、尚未生效的驅動程式繫結） |

值得注意的是：

- **卡頓與斷音大約各半** 來自應用程式（2.0.1 與最初幾個 2.0.2 Beta 的時序錯誤）與環境。經過測量的兩個干擾案例呈現相同的樣貌：傳送位元率降到 550 到 800 kbps，傳送佇列填滿，介面卡的通道對應變成 79 / 79。
- **連線問題大多是應用程式**，而且幾乎都在同一條路徑上：耳機開機後自己發起連線。藍牙模擬器無法驅動這條路徑，因此這些修正都仰賴使用者的記錄。
- **「缺少轉碼器」與「位元率卡住」是耳機** 在決定要向 PC 提供什麼，通常由它們的專用應用程式左右。
- 有些問題 **看起來像無線電問題，但其實不是**：某個型號使用 AAC 時無聲（訊框格式）、耳機關機後 Windows 的輸出仍留在虛擬線路上、切換轉碼器重新連線時喇叭有幾秒聲音、有線耳機也有聲音（系統回送的運作方式）。

## 回報 {#reporting}

如果上述檢查沒有找到原因，請開啟一則 [錯誤回報](https://github.com/SeiyaFunaokaJP/A2DP-Windows-Bridge/issues/new?template=bug_report.yml)，並勾選您已試過的項目。能讓無線問題的回報快速釐清的是：

1. **診斷 > 回報問題**，將 **詳細記錄** 設為 **詳細（debug）**，然後重現問題。
2. **診斷套件**（開啟 **包含 HCI 擷取** 後按 **診斷套件 > 儲存…**，然後 **在 GitHub 上回報**）。它包含串流健康狀況的記錄行（傳送佇列、捨棄的封包、訊號、AFH 通道隨時間的變化）以及失敗連線的 HCI 擷取，能顯示封包在哪裡停住。
3. 問題發生時 **連線品質的截圖**。
4. 使用 **SBC 或 AAC** 以及 **較低位元率** 時是否也會發生。
5. 您對表單中雙重連線、另一個藍牙介面卡與 Wi-Fi 問題的回答。
